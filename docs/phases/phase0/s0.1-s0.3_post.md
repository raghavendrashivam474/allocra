## 7. Problems Encountered & Mitigations

Several issues arose during implementation. Each was investigated, understood, and mitigated without violating the brief's constraints.

### Problem 1 — PowerShell String Interpolation Corrupted JavaScript Files

**Symptom:**
```
SyntaxError: Unexpected identifier 'Server'
console.log([Allocra Server] Running on http://localhost:);
```

**Root cause:**
`server.js` was created using PowerShell's expandable here-string (`@"..."@`). PowerShell interpreted `${PORT}` as a shell variable and stripped backticks intended as JavaScript template literals.

**Mitigation:**
Rewrote all JS/JSX files using verbatim here-strings (`@'...'@`). Verbatim strings do not perform interpolation, preserving JavaScript template literal syntax exactly.

**Lesson:**
Any tool that generates code containing `${...}` or backticks must be run in verbatim/literal string mode.

---

### Problem 2 — Working Directory Mismatch in Script

**Symptom:**
```
Could not find part of the path 'C:\...\allocra\server\server\data\connection.js'
```

**Root cause:**
When re-running the fix script, the terminal's working directory was already inside `allocra\server`. The relative path `server/data/connection.js` produced a duplicated `server\server\...` path.

**Mitigation:**
Rewrote the script to use **absolute paths** based on a fixed `$base` variable, making the script independent of the current working directory.

**Lesson:**
Scripts intended to be re-runnable should never depend on the caller's working directory.

---

### Problem 3 — MongoDB Connection Refused

**Symptom:**
```
[MongoDB] Connection error: connect ECONNREFUSED ::1:27017, connect ECONNREFUSED 127.0.0.1:27017
```

**Root cause:**
The default `.env.example` template used a local MongoDB URI (`mongodb://localhost:27017/allocra`), but the developer environment uses **MongoDB Atlas** — no local `mongod` service exists.

**Mitigation:**
1. Confirmed with the developer that Atlas is being used.
2. Updated `server/.env` with the Atlas connection string.
3. Explicitly loaded `.env` using an absolute path derived from the module's own directory (`import.meta.url`), preventing silent load failures.

---

### Problem 4 — Environment Variable Naming Mismatch

**Symptom:**
```
[Config] Attempting to connect with URI starting with: UNDEFINED
[Config Error] MONGODB_URI is undefined in server/.env
```

**Root cause:**
The `.env` file used `MONGO_URI`, while the code expected `MONGODB_URI`.

**Mitigation:**
Made `server.js` accept both `MONGODB_URI` and `MONGO_URI` for backwards compatibility:
```js
const MONGODB_URI = process.env.MONGODB_URI || process.env.MONGO_URI;
```

**Follow-up:** The `.env.example` remains standardized on `MONGODB_URI` as the canonical name. This tolerance is a pragmatic decision, not a permanent one.

---

### Problem 5 — Corrupted `package.json` Files Breaking Vite/PostCSS

**Symptom:**
```
[plugin:vite:css] Failed to load PostCSS config
SyntaxError: Unexpected token '', "{ "name"... is not valid JSON
```

**Root cause:**
Some `package.json` files, when created via PowerShell's `Set-Content` with UTF-8 encoding, included a **UTF-8 Byte Order Mark (BOM)** at the start of the file. Vite's PostCSS loader uses strict `JSON.parse`, which rejects any leading BOM byte.

**Mitigation:**
Regenerated all three `package.json` files (`root`, `client`, `server`) using **Node.js** directly (`fs.writeFileSync` with default UTF-8 encoding, which does **not** emit a BOM). This produced clean, standards-compliant JSON that Vite parsed successfully.

**Lesson:**
For JSON files intended for strict parsers, always use a generator that emits UTF-8 without a BOM.

## 11. Recommendations for Next Sprint (Phase 1)

The following are not part of Phase 0 but should be considered when planning subsequent work:

1. **Introduce a lightweight service-configuration convention** if a second domain module is added, but only when needed.
2. **Standardize environment variable naming** — deprecate the `MONGO_URI` fallback once no code depends on it. Track via ADR.
3. **Add automated tests** — Phase 0 verification was manual. Introducing a test runner (e.g. Vitest / Jest) as the second domain feature is built is worth considering.
4. **CI setup** — a simple GitHub Actions workflow for linting and starting the server would prevent regression on JSON/env issues encountered during Phase 0.

None of the above should be pre-implemented until an actual sprint requires them.
