## 3. S0.4 — Verification & Regression Foundation

### 3.1 What Was Implemented

#### 3.1.1 Test Strategy Selection

A single test runner — **Vitest** — was adopted for both backend and frontend workspaces. This decision was driven by:

- Native ESM support (both `server` and `client` use `"type": "module"`).
- Zero additional configuration friction with the existing Vite frontend build.
- Fast execution and built-in assertion library.

Supporting libraries:

| Layer | Library | Purpose |
|---|---|---|
| Backend API | `supertest` | HTTP-level assertions against Express `app` |
| Backend Persistence | `mongodb-memory-server` | Isolated in-memory MongoDB for domain tests |
| Frontend Components | `@testing-library/react` | DOM-level UI state assertions |
| Frontend Interaction | `@testing-library/user-event` | Simulated user clicks and typing |
| Frontend Environment | `jsdom` | Browser-like DOM in Node.js |

### 3.2 Problems Faced & Mitigations

#### Problem 1: UTF-8 BOM Corruption of `package.json`

**Symptom:** After writing `package.json` via PowerShell's `Set-Content -Encoding utf8`, the backend institution test suite crashed immediately with:
```
SyntaxError: Unexpected token '', "{\n  "name"... is not valid JSON
```
The error originated inside `mongodb-memory-server-core/src/util/resolveConfig.ts` when it attempted to `JSON.parse()` the nearest `package.json`.

**Root Cause:** PowerShell's `-Encoding utf8` parameter writes a 3-byte UTF-8 Byte Order Mark (`0xEF 0xBB 0xBF`) at the start of the file. Node.js's `JSON.parse()` does not tolerate a BOM and throws a `SyntaxError` on the invisible leading characters.

**Mitigation:** Replaced all file writes with .NET's `[System.IO.File]::WriteAllText()` using an explicit `UTF8Encoding($false)` instance (no BOM):
```powershell
$utf8NoBom = New-Object System.Text.UTF8Encoding($false)
[System.IO.File]::WriteAllText($path, $content, $utf8NoBom)
```
This applies to `package.json`, `.gitignore`, `server/.env.example`, `server/vitest.config.js`, and all other generated files.

**Lesson:** Any PowerShell-based code generation in Node.js projects must use BOM-free UTF-8 encoding. This is a known Windows-specific pitfall.

---

#### Problem 2: `mongodb-memory-server` Binary Download Timeout

**Symptom:** The first execution of `npm test` in the server workspace failed with:
```
Error: Hook timed out in 10000ms.
```
The `beforeAll` hook in `institution.test.js` calls `MongoMemoryServer.create()`, which on first run downloads the MongoDB server binary (~720–780 MB). The download reached approximately 94.5% before the default 10-second Vitest `hookTimeout` expired.

**Initial Attempt:** Increased `hookTimeout` to 120,000ms (2 minutes) in `server/vitest.config.js` and passed `120000` as the third argument to `beforeAll()`.

**Second Failure:** Even at 120 seconds, the download was still in progress (the binary download resumed from a partial `.downloading` file but had to re-validate and extract). The hook timed out again at 120,000ms.

**Root Cause:** The combination of network speed, binary size (~720 MB), and extraction time exceeded even the extended timeout on the first run. Additionally, the `afterAll` hook threw a secondary `TypeError: Cannot read properties of undefined (reading 'stop')` because `mongoServer` was never assigned when `beforeAll` timed out.

**Mitigation (two-part):**

1. **Guarded teardown:** Updated `afterAll` to check for `undefined` before calling `.stop()`:
   ```js
   afterAll(async () => {
     if (mongoose.connection.readyState !== 0) {
       await mongoose.disconnect();
     }
     if (mongoServer) {
       await mongoServer.stop();
     }
   });
   ```

2. **Pre-cache the binary:** Created a standalone diagnostic script (`server/check-mongo.js`) that calls `MongoMemoryServer.create()` outside of any test timeout context. This allowed the download to complete fully (~0.8s startup once cached). The script was deleted after use.

**Result:** Subsequent test runs complete the full backend suite (11 tests) in approximately 10–12 seconds, with the in-memory MongoDB starting in under 1 second from cache.

**Recommendation for CI:** In CI pipelines, add a dedicated cache step for `~/.cache/mongodb-binaries` or set the `MONGOMS_DOWNLOAD_URL` environment variable to a pre-staged binary to avoid first-run download delays entirely.

#### Problem 3: Pre-existing Uncommitted Test Files

**Symptom:** The working tree contained partially implemented test files (`server/tests/health.test.js`, `server/tests/institution.test.js`, `client/src/features/institution/InstitutionView.test.jsx`, `client/src/test/setup.js`) that were untracked and uncommitted.

**Assessment:** The test code itself was well-structured and aligned with the S0.4 brief. The tests covered the correct contracts. The issues were:
- No `vitest.config.js` for the server (timeouts not configured).
- Tests had never been executed successfully (BOM and download issues).
- No root-level `npm test` command existed.

**Decision:** Rather than rewriting the tests, we preserved the existing test implementations, fixed the configuration and environment issues preventing them from running, and added the missing infrastructure (root scripts, vitest config, guarded teardown). This aligns with the brief's core directive: *"Do not rebuild Phase 0."*

## 4. S0.5 — Seed Hardening & Developer Readiness

### 4.1 What Was Implemented

#### 4.1.1 Environment Configuration Standardization

**Finding:** The `server/.env` file used `MONGO_URI` while `.env.example` used `MONGODB_URI`. The `server.js` entry point already tolerated both via fallback:
```js
const MONGODB_URI = process.env.MONGODB_URI || process.env.MONGO_URI;
```

**Decision:** Retained the dual-variable fallback for backward compatibility. `MONGODB_URI` is documented as canonical in both `.env.example` and `server/.env.example`. This was recorded in ADR-0002.

**Action:** Created `server/.env.example` (previously missing) with:
```env
PORT=5000
MONGODB_URI=mongodb://localhost:27017/allocra
```

#### 4.1.2 Configuration Validation

The existing `server.js` already validates the presence of a MongoDB URI at startup:
```js
if (!MONGODB_URI) {
  console.error('[Config Error] Neither MONGODB_URI nor MONGO_URI found in server/.env');
  process.exit(1);
}
```
This was reviewed and confirmed adequate. No credentials are logged. The error message is actionable.

#### 4.1.3 Error Handling Review

The existing centralized error handler in `app.js` was reviewed:
```js
app.use((err, req, res, next) => {
  console.error('[Server Error]', err.message || err);
  const status = err.statusCode || 500;
  res.status(status).json({ error: err.message || 'Internal server error' });
});
```

**Assessment:** This correctly maps domain-level `statusCode` properties (set by `institutionService.js` validation errors) to HTTP responses, and falls back to 500 for unexpected errors. No changes were required.

#### 4.1.4 API Boundary Review

The dependency direction was verified:

```
Route (institutionRoutes.js)
  → Controller (institutionController.js)
    → Domain Service (institutionService.js)
      → Model (Institution.js / Mongoose)
```

**Findings:**
- `institutionService.js` has no HTTP awareness (no `req`, `res`, or status codes beyond domain-level error tagging). ✅
- `institutionController.js` handles all HTTP concerns (status codes, JSON responses). ✅
- `InstitutionView.jsx` communicates exclusively through `api/institution.js` fetch wrappers. ✅
- No Mongoose/MongoDB details leak into the frontend. ✅

No architectural violations were identified. No ADR was needed for corrections.

## 8. Recommendations for Phase 1

1. **CI Pipeline:** Add a GitHub Actions (or equivalent) workflow that runs `npm test` on every pull request. Cache `~/.cache/mongodb-binaries` to avoid first-run download delays.
2. **Environment Variable Migration:** Consider deprecating `MONGO_URI` entirely in a future sprint once all developer environments have migrated to `MONGODB_URI`.
3. **Test Expansion:** As Phase 1 introduces Department, Program, Term, and Group domains, follow the same test pattern established here: domain service tests against `MongoMemoryServer`, API contract tests via `supertest`, and UI state tests via `@testing-library/react`.
4. **Error Handling:** The current centralized error handler is adequate for Phase 0. When Phase 1 introduces more complex validation (e.g., constraint conflicts), consider a structured error classification layer.
