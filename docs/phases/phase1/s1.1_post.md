## 3. How It Was Implemented

### 3.1 Inspection-First Approach

Before writing any code, I inspected the following existing files to understand established patterns:

- `server/data/models/Institution.js` — Schema conventions (trim, required messages, `createdAt` default)
- `server/core/institution/institutionService.js` — Service pattern (async/await, manual validation with `error.statusCode`, single-document resolution via `findOne().sort()`)
- `server/controllers/institutionController.js` — Controller pattern (try/catch, `next(error)` for unhandled, `res.status(error.statusCode)` for known validation errors)
- `server/routes/institutionRoutes.js` — Route pattern (Express `Router`, named exports)
- `server/app.js` — Mounting pattern (`app.use('/api/...', routes)`, centralized error handler at the bottom)
- `client/src/api/institution.js` — Fetch wrapper pattern (check `res.ok`, parse error JSON, throw `Error`)
- `client/src/features/institution/InstitutionView.jsx` — Component pattern (useState/useEffect, loading/empty/configured/error states, form submission guard)
- `client/src/app/App.jsx` — Navigation pattern (tab-based sidebar with `activeTab` state)
- `server/tests/institution.test.js` — Test pattern (MongoMemoryServer in `beforeAll`, collection cleanup in `beforeEach`, Supertest for API, direct service calls for domain logic)

Every new file was written to match these conventions exactly. No new patterns, frameworks, or abstractions were introduced.

### 3.2 Data Ownership Model

A key design decision: **the backend owns all relationship logic.**

- When creating a department, the frontend sends only `{ name }`. The service resolves the active institution via `Institution.findOne().sort({ createdAt: -1 })` and stamps `institutionId` automatically.
- When creating a program, the frontend sends `{ departmentId, name }`. The service validates the department exists via `Department.findById()`, inherits `institutionId` from the department, and rejects with 404 if the department is missing.
- The frontend never constructs MongoDB ObjectIds or manages relationship integrity.

### 3.3 Implementation Order

Following the sprint's showcase-first directive:

1. Department model → service → controller → route (manually verified)
2. Program model → service → controller → route (manually verified)
3. Route mounting in `app.js`
4. Backend tests (department + program)
5. Frontend API client
6. Frontend Academic Structure View
7. Navigation shell update
8. Frontend tests
9. Documentation (ADR, architecture, README)

## 4. Problems Faced and Mitigations

### Problem 1: Frontend Error State Test Failure

**Symptom:** The test `displays error messages when API fails` failed. When `fetchInstitution` was mocked to reject with `new Error('Network error loading data')`, the component rendered the generic message *"Please configure your Institution first before accessing Academic Structure."* instead of the actual error message.

**Root Cause:** In `AcademicStructureView.jsx`, the `!institution` branch had a hardcoded fallback string:

```jsx
{!institution && (
  <div className="alert alert-error">
    Please configure your Institution first before accessing Academic Structure.
  </div>
)}
```

When `fetchInstitution` threw, `setError(err.message)` was called correctly, but `institution` remained `null`, so the component entered the `!institution` branch and displayed the hardcoded string — ignoring the `error` state entirely.

**Mitigation:** Changed the `!institution` branch to prioritize the error state:

```jsx
{!institution && (
  <div className="alert alert-error">
    {error || 'Please configure your Institution first before accessing Academic Structure.'}
  </div>
)}
```

This way, if an API failure caused `institution` to be null, the actual error message is displayed. If the user simply hasn't configured an institution yet (no error), the helpful prompt is shown. The test passed immediately after this one-line change.

### Problem 2: README Overwrite vs. Targeted Patch

**Symptom:** My initial approach was to rewrite the entire `README.md` via `Set-Content`. The senior developer correctly flagged this as too aggressive — it risked losing formatting nuances and made the diff unnecessarily large.

**Mitigation:** Switched to targeted regex-based patches using PowerShell's `-replace` operator. Three surgical replacements were applied:

1. Status line: `Phase 0 Hardened` → `Phase 1 — S1.1`
2. Test count: `15 tests` → `38 tests`
3. Project structure map: updated `api/` and `features/` descriptions

This preserved the original file's structure, formatting, and all untouched sections.

### Problem 3: LF/CRLF Line Ending Warnings

**Symptom:** Every `git add` produced warnings like:

```
warning: in the working copy of 'server/data/models/Department.js', LF will be replaced by CRLF the next time Git touches it
```

**Root Cause:** PowerShell's `Set-Content -Encoding utf8` writes files with UTF-8 BOM and LF line endings on Windows. Git's `core.autocrlf` setting (likely `true` on this Windows machine) converts LF to CRLF on checkout, triggering the warning on add.

**Mitigation:** These warnings are cosmetic and do not affect functionality or test results. Git handles the conversion transparently. No action was taken — the warnings are expected on Windows and do not indicate a problem. If they become noisy in future sprints, a `.gitattributes` file can be added to normalize line endings explicitly.

---

### Problem 4: Architecture Decision — Embed vs. Separate Collections

**Symptom:** The sprint brief explicitly warned against expanding the Institution document. However, the natural instinct when building "departments of an institution" is to embed a `departments[]` array inside the Institution schema.

**Mitigation:** Before implementing, I evaluated three options:

| Option | Pros | Cons |
|---|---|---|
| A. Embed in Institution | Single-query reads | Violates Phase 0 contract; aggregate grows unbounded |
| B. Separate collections | Clean boundaries; Institution stays minimal | Requires `populate` for joins |
| C. Generic entity collection | Flexible | Over-engineered for two known concepts |

Chose **Option B** and documented the rationale in ADR-0003. The Institution model remains exactly `{ name, academicYear }` — unchanged from Phase 0.

## 8. Recommendations for S1.2

Based on observations during this sprint:

1. **Line ending normalization:** Consider adding a `.gitattributes` file to enforce consistent LF endings across platforms and eliminate the CRLF warnings.
2. **Institution guard middleware:** Multiple services independently call `Institution.findOne().sort({ createdAt: -1 })`. If S1.2 adds more institution-scoped entities, a shared middleware or utility to resolve the active institution once per request would reduce duplication.
3. **Department deletion:** Currently there is no way to delete a department. If programs exist under it, deletion needs cascade logic. This should be addressed before the UI grows more complex.
4. **Program count on department cards:** The frontend currently filters programs client-side to show counts per department. For larger datasets, this should move to a server-side aggregation.
