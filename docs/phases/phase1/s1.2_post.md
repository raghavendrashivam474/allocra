## 1. Executive Summary

S1.2 successfully extends the Allocra institution configuration experience with two new domain concepts — **Academic Terms** and **Groups/Batches** — producing a browser-demonstrable, API-backed, MongoDB-persisted vertical slice. The implementation follows the exact architectural patterns established in Phase 0 and S1.1, introduces no breaking changes to existing contracts, and adds 26 new automated tests on top of the existing 38.

The sprint's core deliverable is functional: a user can configure an institution, define departments and programs, create academic terms, and then create groups that bind a program to a term — with full cross-institution relationship integrity enforced at the backend.

## 2. What Was Implemented

### 2.1 Domain Models

| Model | Collection | Fields |
|-------|-----------|--------|
| **Term** | `terms` | `institutionId` (ref Institution), `name` (trimmed), `academicYear` (inherited from Institution), `createdAt` |
| **Group** | `groups` | `institutionId` (ref Institution), `programId` (ref Program), `termId` (ref Term), `name` (trimmed), `createdAt` |

Both models are institution-scoped. The Term's `academicYear` is automatically inherited from the active institution at creation time rather than being independently configurable, preventing drift between institution configuration and term metadata.

### 2.2 API Endpoints

| Method | Endpoint | Status Codes | Description |
|--------|----------|-------------|-------------|
| `GET` | `/api/terms` | 200 | Returns `{ terms: [...] }` for the active institution |
| `POST` | `/api/terms` | 201, 400 | Creates a term; requires `{ name }`; resolves institution server-side |
| `GET` | `/api/groups` | 200 | Returns `{ groups: [...] }` populated with `programId` and `termId` |
| `POST` | `/api/groups` | 201, 400, 404 | Creates a group; requires `{ programId, termId, name }`; validates existence and same-institution constraint |

All four endpoints follow the exact response envelope conventions established by the existing `/api/departments` and `/api/programs` endpoints (e.g., `{ message, term }` on 201, `{ error }` on failure).

## 3. How It Was Implemented

### 3.1 Implementation Sequence

The sprint followed the showcase-first order specified in the sprint plan:

1. **Stage A — Term Backend**: Model → Service → Controller → Routes → Mount in `app.js`. Manually verified the API contract before proceeding.
2. **Stage B — Group Backend**: Model → Service (with cross-institution validation) → Controller → Routes → Mount in `app.js`. Verified relationship integrity logic.
3. **Stage C — Browser Slice**: Client API module → `TermsAndGroupsView` component → App.jsx navigation wiring.
4. **Stage D — Hardening**: Backend test suites (term + group) → Frontend test suite → Documentation updates → Full regression verification.

### 3.2 Institution Resolution Strategy

Per Section 19 of the sprint plan, we evaluated whether to centralize the active institution resolution before duplicating it in the new services. After inspecting `departmentService.js` and `programService.js`, we determined:

- The resolution is a single line: `Institution.findOne().sort({ createdAt: -1 })`.
- It appears in four services (department, program, term, group).
- Introducing middleware or a shared utility at this stage would add indirection without meaningful reduction in complexity.
- The application is single-tenant by design; this pattern is unlikely to become a maintenance burden until multi-tenancy is introduced.

**Decision**: Retain the existing per-service resolution pattern. No ADR-0004 was created because no architectural change was made. This decision should be revisited if the number of institution-scoped entities grows significantly or if multi-tenancy is introduced.

### 3.3 Response Shape Standardization

After initially writing `termController.js` and `groupController.js` with simplified response shapes, we inspected the existing `departmentController.js` and `programController.js` and discovered the established convention:

- List endpoints return `{ entities: [...] }` (e.g., `{ departments: [...] }`)
- Create endpoints return `201` with `{ message, entity }` (e.g., `{ message: 'Department created successfully', department: {...} }`)
- Validation errors use `error.statusCode` to return `res.status(code).json({ error: message })`

We rewrote both new controllers to match this convention exactly, ensuring frontend code can rely on consistent response shapes across all institution-scoped endpoints.

## 4. Problems Faced and Mitigations

### 4.1 Cross-Institution Test Failure

**Problem**: The cross-institution relationship integrity test initially failed. The test created Institution 1 via `Institution.create()`, then created Institution 2 via `institutionService.saveInstitution()`, then created a term via `termService.createTerm()`. The test expected `groupService.createGroup()` to reject the combination of a program from Institution 1 and a term from Institution 2. Instead, the group was created successfully.

**Root Cause**: `institutionService.saveInstitution()` performs an upsert-like operation that updates the most recent institution rather than always creating a new one. Since `termService.createTerm()` resolves the active institution via `Institution.findOne().sort({ createdAt: -1 })`, the term ended up belonging to the same institution as the program, making the cross-institution check pass when it should have failed.

**Mitigation**: Rewrote the test to create both institutions directly via `Institution.create()` and the cross-institution term directly via `Term.create()` with an explicit `institutionId`. This bypasses the service-layer resolution and tests the actual domain constraint in `groupService.createGroup()` — which is the correct layer to validate. The test now correctly verifies that `program.institutionId.toString() !== term.institutionId.toString()` triggers a 400 rejection.

**Lesson**: When testing domain constraints that involve multiple institution contexts, bypass service-layer institution resolution and construct the exact data scenario at the model layer. The service layer's resolution logic is a separate concern from the relationship integrity logic being tested.

### 4.2 PowerShell Backtick Escaping in README.md

**Problem**: When updating `README.md` via a PowerShell here-string, the backtick in `` `v1.2 `` was interpreted as a PowerShell escape character, producing a vertical tab character (`\v`) in the output file. The rendered markdown showed `S1.2 (1.2)` instead of `` S1.2 (`v1.2`) ``.

**Mitigation**: Applied a targeted regex replacement to fix the corrupted line:
```powershell
$readme = [regex]::Replace($readme, '## Current Status: Phase 1 — S1\.2 \(.*?\)', '## Current Status: Phase 1 — S1.2 (`v1.2`)')
```
Subsequent patches used regex-based section replacement rather than full-file here-strings to avoid further escaping issues.

### 4.3 Controller Response Shape Mismatch

**Problem**: The initial `termController.js` returned raw arrays from `getTerms()` and raw documents from `createTerm()`, inconsistent with the `{ departments }` / `{ message, department }` envelope used by existing controllers.

**Mitigation**: After inspecting `departmentController.js` and `programController.js`, rewrote both new controllers to match the established convention. This was caught during the inspection phase before frontend integration, so no frontend code was affected.

## 8. Recommendations for S1.3

1. **Revisit institution resolution** if S1.3 introduces additional institution-scoped entities (e.g., Faculty, Rooms, Subjects). At that point, a shared utility or middleware may be justified.
2. **Design deletion/cascade semantics** before allowing term or group removal. Deleting a term that has associated groups requires an intentional decision (cascade delete, soft delete, or prevent deletion).
3. **Consider term ordering and academic calendar structure** when building scheduling features. The current Term model is intentionally minimal; future sprints may need `startDate`, `endDate`, `termType`, or `sequence`.
4. **The Group model is ready for student enrollment and allocation features** in upcoming sprints. The `programId + termId` composite provides a natural key for section-based scheduling.
