## 3. Technical Implementation Details

### 3.1 Domain Representation

Working days use a canonical string enum throughout the entire stack:

```
MONDAY | TUESDAY | WEDNESDAY | THURSDAY | FRIDAY | SATURDAY | SUNDAY
```

The UI displays human-readable labels ("Monday", "Tuesday", etc.) while the API, service, model, validation, and tests all operate on the canonical uppercase values. This ensures consistency and eliminates ambiguity in downstream scheduling logic.

### 3.2 Persistence Strategy

The Calendar model uses a **unique index on `institutionId`** combined with `findOneAndUpdate` using `{ upsert: true }` to guarantee exactly one calendar document per institution. This prevents duplicate configurations from accumulating through repeated saves:

```
Institution A
  └── Calendar (single document, updated in place)
        └── workingDays: ["MONDAY", "TUESDAY", ...]
```

### 3.3 Validation Contract

The service layer enforces the following validation rules before any persistence operation:

| Rule | Behavior | HTTP Status |
|---|---|---|
| `workingDays` must be present | Reject missing field | 400 |
| `workingDays` must be an array | Reject strings, numbers, objects | 400 |
| Array must contain at least one day | Reject empty arrays | 400 |
| All values must be valid day enums | Reject unknown strings (e.g., "FUNDAY") | 400 |
| Duplicate values | Silently deduplicated via `Set` | 200 |
| Institution must exist | Reject if no institution configured | 400 |

### 3.4 API Surface

| Method | Endpoint | Request Body | Response |
|---|---|---|---|
| `GET` | `/api/calendar` | — | `{ calendar: { workingDays: [...] } }` or `{ calendar: null }` |
| `PUT` | `/api/calendar` | `{ workingDays: [...] }` | `{ message, calendar }` or `{ error }` |

The `PUT` verb was chosen over `POST` to reflect the idempotent, configuration-oriented nature of the operation (create-or-update semantics rather than resource creation).

### 3.5 Architecture Decision: No New Abstraction

The sprint brief identified S1.3 as a checkpoint to evaluate whether a shared institution resolver (e.g., `institutionMiddleware.js` or `BaseInstitutionService.js`) was warranted, given that `Institution.findOne().sort({ createdAt: -1 })` now appears in approximately four services.

**Decision: Retain the existing pattern.** The duplication is a single line in each service, the system remains single-tenant, and introducing a shared abstraction at this stage would add indirection without meaningful reduction in complexity. This decision is consistent with the project's "no speculative abstractions" rule documented in `docs/architecture.md`.

## 4. Problems Encountered and Mitigations

### 4.1 PowerShell Here-String Interpolation Corrupting JSX Template Literals

**Problem:** When generating React component files via PowerShell double-quoted here-strings (`@"..."@`), the backtick character (`` ` ``) and dollar sign (`$`) in JSX template literals (e.g., `` className={`allocra-nav-item ${activeTab === 'calendar' ? 'active' : ''}`} ``) were interpreted by PowerShell as escape sequences and variable interpolation operators. This produced syntactically broken output in `App.jsx`:

```jsx
// Expected:
className={`allocra-nav-item ${activeTab === 'calendar' ? 'active' : ''}`}

// Actual (corrupted):
className={llocra-nav-item \}
```

This caused a runtime `ReferenceError: allocra is not defined` crash in the browser, though the frontend unit tests passed because they mock the component in isolation.

**Mitigation:** Switched all file-generation commands to use **single-quoted here-strings** (`@'...'@`), which completely disable PowerShell variable expansion and escape processing. The file contents are written verbatim. This was applied to the final rewrite of `App.jsx` and all subsequent file creation steps.

**Lesson Learned:** When using PowerShell to scaffold files containing JavaScript template literals, always use single-quoted here-strings. Double-quoted here-strings are only safe for files that contain no backticks or dollar signs.

---

### 4.2 UTF-8 BOM and Encoding Corruption in Documentation Files

**Problem:** Windows PowerShell's `Set-Content` cmdlet defaults to the system's ANSI code page (Windows-1252 on most Western systems), not UTF-8. When writing `README.md` — which contains Unicode box-drawing characters (`├──`, `│`, `└──`) in the project directory tree — the encoding mismatch produced mojibake:

```
# Expected:
│   ├── api/

# Actual (corrupted):
â"‚   â"œâ"€â"€ api/
```

Additionally, even when using `[System.IO.File]::WriteAllText()` with `[System.Text.Encoding]::UTF8`, the .NET UTF-8 encoder prepends a Byte Order Mark (BOM: `EF BB BF`) by default, which can cause issues with certain toolchains and linters.

**Mitigation:** Adopted a strict encoding protocol for all documentation writes:
1. **Read** using `[System.IO.File]::ReadAllText($path, [System.Text.Encoding]::UTF8)` to correctly decode existing UTF-8 content.
2. **Write** using `New-Object System.Text.UTF8Encoding($false)` (the `$false` parameter disables BOM emission) passed to `[System.IO.File]::WriteAllText()`.

This ensured clean, BOM-free UTF-8 output that preserves all Unicode characters.

### 4.3 String Replacement Failures in Documentation Patches

**Problem:** When applying incremental patches to `docs/architecture.md` using PowerShell's `-replace` operator and `.Replace()` method, several replacements silently failed or threw parse errors. The root causes were:

1. **Operator precedence conflicts:** Target strings containing `**` (Markdown bold), `&` (ampersand), and `-` (dash) were interpreted by PowerShell as arithmetic, bitwise, and unary operators when embedded in double-quoted strings.
2. **Line-ending mismatches:** The `.Contains()` and `.Replace()` methods perform exact byte-level matching. Files with mixed `\r\n` (Windows) and `\n` (Unix) line endings caused target strings to fail matching even when the visible text appeared identical.

**Mitigation:** Abandoned string-matching approaches entirely for documentation patches. Instead, adopted a **line-by-line array insertion** strategy:
1. Read the file as an array of lines using `[System.IO.File]::ReadAllLines()`.
2. Iterate through lines, appending each to a new list.
3. When a line matches a regex pattern (e.g., `^- \*\*Group\*\*:\s*` + backtick + `name`), insert the new line immediately after it.
4. Write the modified array back using `[System.IO.File]::WriteAllLines()`.

This approach is immune to line-ending variations, special character escaping issues, and multi-line matching problems.

---

### 4.4 Sidebar Navigation Button Not Injected by Regex

**Problem:** The initial attempt to inject the "Calendar" navigation button into `App.jsx` used a PowerShell `-replace` regex targeting the multi-line "Terms & Groups" button block. The regex failed to match due to whitespace and line-ending differences between the pattern and the actual file content, resulting in the button being silently omitted from the sidebar.

**Mitigation:** Rather than debugging increasingly complex multi-line regex patterns, the entire `App.jsx` file was rewritten cleanly using a single-quoted here-string (per Mitigation 4.1). This guaranteed correct output and eliminated the fragility of regex-based partial file modifications for JSX content.

## 8. Recommendations

1. **Adopt single-quoted here-strings as the default** for all future PowerShell-based file scaffolding in this project, given the prevalence of JSX template literals and JavaScript string interpolation.
2. **Standardize on BOM-free UTF-8** for all documentation writes using the `UTF8Encoding($false)` pattern established in this sprint.
3. **Prefer line-array insertion over string replacement** for incremental documentation patches to avoid encoding and escaping edge cases.
4. **Revisit the institution resolver abstraction** at the S1.5 or Phase 2 checkpoint, when the number of institution-scoped services is expected to grow significantly.
