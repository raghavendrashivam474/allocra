# 5. Persistence Strategy

The Time Model uses a **single-document persistence boundary**.

Rather than introducing independent collections for every time concept, periods and breaks are embedded within the institution's Time Model.

Conceptually:

```text
Institution A
    │
    └── TimeModel
          │
          ├── Period 1
          ├── Period 2
          ├── Break
          └── Period 3
```

This keeps the configuration cohesive and allows the entire time model to be validated and saved as one logical configuration.

The model is institution-scoped and protected by a unique institution association.

This supports the intended invariant:

> One active Time Model configuration per institution.

The service provides the domain-level operations required by the Time Model.

The primary responsibilities include:

The service remains responsible for domain correctness rather than delegating business rules to the controller or frontend.

# 7. Time Validation Contract

The Time Model establishes a strict time representation based on the 24-hour:

```text
HH:mm
```

format.

Examples:

```text
09:00
09:50
13:30
17:00
```

The service validates that:

```text
startTime < endTime
```

Therefore:

```text
09:00 → 09:50
```

is valid.

While:

```text
10:00 → 09:00
```

is invalid.

Likewise:

```text
09:00 → 09:00
```

is invalid because an interval must have positive duration.

This validation is enforced at the domain-service layer rather than relying solely on browser validation.

---

# 8. Cross-Interval Overlap Validation

A major responsibility introduced in S1.4 is ensuring that the configured time model represents one coherent chronological structure.

For example, the following configuration is invalid:

```text
Period 1
09:00–10:00

Period 2
09:30–10:30
```

because the intervals overlap.

The same validation applies across interval types.

For example:

```text
Period
09:00–10:00

Break
09:30–09:45
```

is also invalid.

The Time Model therefore prevents ambiguous or contradictory time configurations before persistence.

---

# 9. Touching Intervals

Intervals that meet exactly at a boundary are valid.

For example:

```text
Period 1
09:00–09:50

Period 2
09:50–10:40
```

is valid.

Likewise:

```text
Period
09:00–09:50

Break
09:50–10:00
```

is valid.

The implementation distinguishes between:

```text
overlap
```

and:

```text
boundary contact
```

This is important because normal academic schedules commonly place consecutive periods directly against each other.

---

# 10. Deterministic Chronological Ordering

The service establishes deterministic chronological ordering for the configured intervals.

The system should therefore represent a schedule in a predictable sequence such as:

```text
09:00–09:50
09:50–10:40
10:40–11:00
11:00–11:50
```

The implementation does not rely on arbitrary document or insertion ordering for the semantic sequence of time intervals.

This gives future scheduling logic a stable time representation to consume.

---

# 11. Atomic Save Semantics

The Time Model uses atomic create-or-update behavior.

The intended lifecycle is:

```text
No Time Model
      ↓
Save
      ↓
Create configuration
```

and:

```text
Existing Time Model
      ↓
Save updated configuration
      ↓
Update existing configuration
```

Repeated saves therefore do not create uncontrolled duplicate Time Model documents.

The persistence boundary remains a single logical configuration.

This is consistent with the configuration-oriented nature of the feature.
