## 1. Executive Summary

Sprint S1.5 is the capstone sprint of Phase 1. Its objective was to transform Allocra from a collection of four independent configuration screens into a coherent institution setup experience with an authoritative readiness assessment. The sprint delivered a unified **Setup Workspace** frontend, a cross-domain **Configuration Readiness** backend service and API, and the supporting test infrastructure — all without modifying any existing S1.1–S1.4 domain logic, APIs, or persistence boundaries.

Phase 1 is now complete. Allocra can represent an institution's foundational academic structure, temporal model, and calendar configuration, and can programmatically determine whether that foundation is sufficient to proceed to Phase 2 (Resources & Activities).

## 2. What Was Implemented

### 2.1 Backend: Setup Readiness Service

**File:** `server/core/institution/setup/setupReadinessService.js`

A read-only orchestration service that evaluates Phase-1 configuration completeness by querying all seven existing Mongoose models (`Institution`, `Department`, `Program`, `Term`, `Group`, `Calendar`, `TimeModel`) at request time.

**Readiness rules implemented:**

| Check | Condition for "Complete" |
|---|---|
| Institution | At least one institution document exists |
| Academic Structure | At least one department AND one program linked to the institution |
| Terms & Groups | At least one term AND one group linked to the institution |
| Calendar | Calendar document exists with at least one working day |
| Time Model | Time model document exists with at least one period |

**Key design decisions:**
- The service queries Mongoose models directly rather than calling existing domain service methods. This is intentional: domain services are mutation-oriented (create, save, validate), while readiness is a read-only cross-cutting inspection concern. Coupling readiness to mutation services would create unnecessary dependencies and potential side effects.
- Readiness is derived dynamically — no new MongoDB collection, no cached state, no `SetupStatus` document. This eliminates synchronization problems and ensures the readiness assessment is always consistent with actual data.
- Institution resolution uses the same `Institution.findOne().sort({ createdAt: -1 })` pattern established in S1.3/S1.4, maintaining consistency without introducing a new resolver abstraction.
- When no institution exists, the service short-circuits and returns all five checks as incomplete, avoiding unnecessary database queries.

### 2.2 Backend: API Endpoint

**Files:** `server/controllers/setupController.js`, `server/routes/setupRoutes.js`

Single endpoint: `GET /api/setup/readiness`

**Response contract:**
```json
{
  "ready": false,
  "checks": [
    {
      "key": "institution",
      "label": "Institution",
      "status": "complete",
      "message": "Institution is configured."
    },
    {
      "key": "academic-structure",
      "label": "Academic Structure",
      "status": "incomplete",
      "message": "No department or program has been configured."
    }
  ]
}
```

The response follows existing API conventions: plain JSON body, no wrapper envelope (consistent with how `GET /api/calendar` returns `{ calendar: ... }`), human-readable messages suitable for direct UI display, and machine-readable `key`/`status` fields for programmatic consumption.

The route is registered in `server/app.js` as `app.use('/api/setup', setupRoutes)`, following the existing mount pattern.

### 2.3 Frontend: Setup Workspace Component

**Files:** `client/src/features/setup/SetupWorkspace.jsx`, `client/src/api/setup.js`

The Setup Workspace provides:

- **Readiness Banner:** A prominent status indicator at the top of the workspace. When `ready: true`, it displays a green confirmation that the institution is prepared for Phase 2. When `ready: false`, it displays an amber warning with a bulleted list of specific incomplete items and their human-readable explanations.

- **Configuration Cards Grid:** Five cards (one per Phase-1 domain) displayed in a responsive CSS grid. Each card shows the domain label, a status badge ("✓ Configured" or "✕ Incomplete"), the readiness message (e.g., "3 department(s) and 6 program(s) configured."), and an action button.

- **Navigation Integration:** Each card's action button ("Configure" for incomplete items, "Manage" for complete items) accepts an `onNavigate(tabName)` callback prop, enabling direct navigation to the relevant configuration screen without requiring the user to manually find it in the sidebar.

- **State Handling:** Loading state (text indicator), error state (alert with retry button), and empty/partial configuration states are all handled gracefully.

### 2.4 Frontend: App Shell Integration

- The Setup Workspace is now the default landing view (`activeTab` defaults to `'setup'` instead of `'overview'`).

## 4. Problems Encountered & Mitigations

### 4.1 MongoDB Connection Timeout in Test Suite

**Problem:** The initial `setupReadiness.test.js` imported Mongoose models and called `Institution.deleteMany({})` in `beforeEach` without first establishing a database connection. All 5 tests failed with:
```
MongooseError: Operation `institutions.deleteMany()` buffering timed out after 10000ms
```

**Root Cause:** Unlike the existing test files (e.g., `calendar.test.js`), the new test file did not include `MongoMemoryServer` lifecycle hooks (`beforeAll`/`afterAll`) to spin up an in-memory MongoDB instance and connect Mongoose before running queries.

**Mitigation:** Inspected `server/tests/calendar.test.js` to identify the exact connection pattern used across the project:
```javascript
beforeAll(async () => {
  mongoServer = await MongoMemoryServer.create();
  const uri = mongoServer.getUri();
  await mongoose.connect(uri, { dbName: 'allocra-test-setup-readiness' });
}, 120000);
```
Adopted this pattern verbatim, using a unique `dbName` to prevent cross-test contamination. All 5 tests passed immediately after this fix.

**Lesson:** Always inspect existing test infrastructure before writing new test files. The project uses per-test-file `MongoMemoryServer` instances rather than a shared global setup.

### 4.2 PowerShell String Interpolation Destroying JavaScript Template Literals

**Problem:** After fixing the database connection, 3 of 5 tests still failed with assertions like:
```
expected 'No  has been configured.' to contain 'department'
expected ' working day(s) configured.' to contain '5 working day(s)'
```

The readiness messages were returning empty strings where dynamic values should have been interpolated (e.g., `${deptCount}` became empty, `${calendar.workingDays.length}` became empty).

**Root Cause:** The `setupReadinessService.js` file was generated via a PowerShell `@"..."@` (double-quoted) here-string. PowerShell interprets `${...}` as PowerShell variable interpolation, not JavaScript template literal syntax. Since `$deptCount`, `$progCount`, etc. are not defined PowerShell variables, they evaluated to empty strings before the file was ever written to disk. The resulting JavaScript file contained literal empty strings instead of template expressions.

**Mitigation:** Rewrote the file generation using PowerShell's `@'...'@` (single-quoted) here-string, which preserves all content literally without any variable interpolation. Verified the fix by inspecting the generated file contents and re-running the test suite — all 5 tests passed.

**Lesson:** When generating source code files via PowerShell scripts, always use single-quoted here-strings (`@'...'@`) to prevent unintended interpolation of `$` characters that are meaningful in the target language.

### 4.3 Testing-Library Duplicate Element Queries

**Problem:** Two frontend tests failed with:
```
TestingLibraryElementError: Found multiple elements with the text: /No institution has been configured\./i
```

The same message text appeared in both the readiness banner's `<ul>` summary list and the individual configuration card's `<p class="item-message">` element.

**Root Cause:** This is actually correct component behavior — the workspace is designed to show status information in both the summary banner and the detail cards. However, `screen.getByText()` throws when it finds more than one matching element, as it expects a unique match.

**Mitigation:** Updated the affected test assertions to use `screen.getAllByText()` and verify `length > 0` instead of expecting a single unique match:
```javascript
const messages = screen.getAllByText(/No institution has been configured\./i);
expect(messages.length).toBeGreaterThan(0);
```
This correctly validates that the message is present in the rendered output without enforcing uniqueness where the UI intentionally duplicates information.

**Lesson:** When a component displays the same information in multiple locations by design (summary + detail), tests must use `*AllBy*` queries rather than singular `getBy*` queries.

### 4.4 README.md Encoding Artifact

**Problem:** The existing `README.md` contained a corrupted Unicode em-dash in the status header: `Phase 1 â€" S1.3` instead of `Phase 1 — S1.3`. This made precise regex matching unreliable.

**Mitigation:** Used a broader regex pattern (`Phase 1 [^\r\n]*`) to match the entire status line regardless of encoding artifacts, replacing it with the clean S1.5 status string.
