## 3. S2.3 — Academic Activities Foundation

### 3.1 Objective

Introduce the domain concept of an **Activity** — the academic unit that will eventually be allocated into a (time × resource) combination by Phase 3 — **without** encoding any allocation, scheduling, or assignment semantics.

The brief defined this boundary explicitly:

> *"S2.3 answers: What activities exist? S2.4 answers: Which resources can participate in those activities? Phase 3 answers: Which resources are actually allocated to an activity?"*

### 3.3 Domain Model Design

Following the brief's "Minimal / Institution-scoped / Academically scoped / Allocation-ready / Not allocation-aware" constraints:

**`server/data/models/Activity.js`**

| Field | Type | Required | Purpose |
|---|---|---|---|
| `institutionId` | `ObjectId → Institution` | Yes | Institution isolation |
| `groupId` | `ObjectId → Group` | Yes | Full academic context inherited through Group |
| `name` | `String` (trimmed) | Yes | Activity identity (e.g., "Data Structures") |

**Deliberately omitted** (per brief Section 6 — "Allocation-aware fields"):
`assignedFaculty`, `assignedRoom`, `assignedPeriod`, `allocationStatus`, `schedule`, `conflicts`, `solverScore`, `priority`, `availability`, `workload`.

### 3.4 Service Layer

**`server/core/institution/academic-context/activityService.js`**

The service mirrors `facultyService.js` exactly in style, structure, and error handling:

- **Active institution resolution:** `Institution.findOne().sort({ createdAt: -1 })` — identical pattern to Faculty.
- **Error style:** `new Error('msg')` with `error.statusCode` property attached.
- **Validation sequence:**
  1. `groupId` presence (400)
  2. `name` presence and non-empty after trim (400)
  3. `groupId` ObjectId validity (400)
  4. Group existence (404)
  5. Institution configured (400)
  6. **Cross-institution rejection:** `group.institutionId !== institution._id` (400)
  7. **Duplicate prevention:** same (`institutionId`, `groupId`, `name`) rejected (409)
- **Return shape:** `.populate('groupId', 'name')` — matches Faculty's `.populate('departmentId', 'name')`.

## 4. Problems Encountered & Mitigations

Three concrete problems surfaced during S2.3 implementation. All were resolved with surgical fixes; none required an architectural change or an ADR.

### Problem 1 — Incorrect Relative Import Path in Service

**Symptom:**
After creating `activityService.js`, the entire backend test suite failed (12/12 test files errored out) with:
```
Error: Cannot find module '../../../../data/models/Activity.js'
```

**Root cause:**
The initial file used `../../../../data/models/...` (four levels up), but `academic-context/` is only three levels deep from `server/`, not four. The Faculty service lives one level deeper (`resources/faculty/`), which is why its path uses four `../` segments. I had copied the Faculty import pattern mechanically without re-checking depth.

**Mitigation:**
Rewrote `activityService.js` imports to use the correct depth (`../../../data/models/...`). Verified by running the full Jest suite — all 103 pre-existing tests + 11 new tests passed.

**Lesson:**
When mirroring an existing service, confirm the directory depth against the actual folder layout, not against the convention of a different sibling.

---

### Problem 2 — Test Fixture Used Wrong Institution Schema

**Symptom:**
All 11 new activity tests failed with:
```
ValidationError: Institution validation failed: academicYear: Academic year is required
```

**Root cause:**
The test helper `setupAcademicContext()` instantiated `Institution` with `{ name, code }`, but the actual `Institution` schema requires `{ name, academicYear }`. This was an assumption error — `code` is not a field on this model.

**Mitigation:**
Inspected `server/data/models/Institution.js` to confirm the actual schema, then updated the test fixture to use `{ name: 'Tech University', academicYear: '2025-2026' }`. All 11 tests passed on re-run.

**Lesson:**
When writing new test fixtures, verify every parent model's schema rather than assuming field names.

---

### Problem 3 — PowerShell Heredoc Corrupted React Template Literals in `App.jsx`

**Symptom:**
After updating `App.jsx` via a PowerShell double-quoted heredoc (`@"..."@`), the Vite dev server showed:
```
[plugin:vite:react-babel] Unexpected character '⍰'. (71:23)
className={⍰llocra-nav-item ${activeTab === 'activities' ? 'active' : ''}}
```
And later:
```
Uncaught ReferenceError: indicator is not defined
    at App (App.jsx:33:37)
```

**Root cause (two compounding issues):**
1. **PowerShell variable expansion inside `@"..."@` heredocs:** PowerShell treats `${name}` as a variable reference inside double-quoted heredocs. JSX template literals like `` `${serverStatus}` `` and `` `${activeTab === 'setup' ? 'active' : ''}` `` were being evaluated — and in many cases destroyed — by PowerShell before the string ever hit disk. In the `status-indicator` case, PowerShell silently substituted the word `indicator` as an undefined PS variable, producing invalid JavaScript (`status-indicator  ${serverStatus}` lost its leading identifier).
2. **Escape-based mitigation attempt also failed:** Attempting to escape backticks with `` ` `` or `` `$`` created additional subtle corruption, including the stray `⍰` character shown above (a UTF-16 BOM / high-byte artifact from PowerShell's string handling).

Additionally, during an interim recovery attempt, I rewrote `App.jsx` from scratch rather than from the exact baseline — which inadvertently stripped the application's real CSS class names (`allocra-container`, `brand-wrap`, `nav-section-label`, `status-dot status-online`, etc.) and replaced them with placeholder classes that broke the entire visual layout.

**Mitigation (three steps):**
1. **Switched to single-quoted PowerShell heredocs (`@'...'@`)** which perform zero variable expansion. This is the only safe way to write JSX template literals from PowerShell.
2. **Retrieved the exact pre-S2.3 `App.jsx` from git** using `git show HEAD:client/src/app/App.jsx` to recover the authentic layout, CSS classes, and navigation section labels (*Workspace / Institution / Resources*).
3. **Reconstructed the file byte-for-byte**, adding only the three required S2.3 lines:
   - `import ActivitiesView from '../features/activities/ActivitiesView';`
   - The *Activities* `<button>` inside the *Institution* nav section
   - The `{activeTab === 'activities' && <ActivitiesView />}` render block

Verified visually in the browser (sidebar, header, Setup Workspace, and all other tabs render identically to pre-S2.3) and verified all 55 frontend tests pass.

**Lesson:**
When writing files containing shell metacharacters (`$`, `` ` ``, `"`) from PowerShell, **always use single-quoted heredocs (`@'...'@`)**. Never trust double-quoted heredocs for JSX, template literals, or any code using `${}` syntax. When restoring a protected file, always recover its exact baseline from `git show` rather than reconstructing from memory.

## 7. S2.4 — Planning Notes (Not Yet Implemented)

Per the brief's **Architectural Decision Point** (Section 18), the first task of S2.4 is to decide the Activity–Resource relationship representation. Based on the S2.3 model, the options are:

| Option | Shape | Trade-offs |
|---|---|---|
| **A — Embedded arrays on Activity** | `Activity.facultyIds: [ObjectId]`, `Activity.roomIds: [ObjectId]` | Simplest. Natural ownership (Activity owns its eligibility). Good for small cardinalities. Harder to query from the Resource side ("which activities can Prof. X teach?"). |
| **B — Join collections** | `ActivityFaculty { activityId, facultyId }`, `ActivityRoom { activityId, roomId }` | Scales better. Enables bidirectional queries. More collections, more validation surface area, more test code. |
| **C — Mixed** | Embedded for one direction, join for the other | Not justified yet. |

**Preliminary recommendation (pending senior review):** **Option A (embedded arrays).** Rationale:
- Activities are the natural owners of their resource eligibility.
- Current MongoDB conventions in Allocra favor embedded references where ownership is clear (e.g., `Calendar.workingDays`).
- No current UI requires reverse lookup from Resource → Activities.
- If reverse lookup is ever required by Phase 3, it is a trivial `Activity.find({ facultyIds: X })` query.

If this recommendation is accepted, **no ADR is required**. If Option B is preferred, an ADR will be drafted first per Sections 18–19 of the brief.

**S2.4 blocked on:** Senior review of this recommendation.
