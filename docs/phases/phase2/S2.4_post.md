## 1. Executive Summary

S2.4 establishes the **academic eligibility configuration layer** for Allocra. An academic activity (e.g., "Mathematics") can now maintain explicit references to the faculty members eligible to teach it and the rooms suitable for hosting it. These relationships are persisted, validated against institutional boundaries, independently manageable, and exposed through both the API and the existing Activity management UI.

No allocation, scheduling, or conflict-detection logic was introduced. The implementation is a pure eligibility registry, ready to support S2.5 validation and the later Phase 3 allocation engine.

## 2. What Was Implemented

### 2.1 Backend — Domain Layer

**Activity Model** (`server/data/models/Activity.js`)

Extended the existing Mongoose schema with two embedded reference arrays:

```javascript
facultyIds: [{ type: mongoose.Schema.Types.ObjectId, ref: 'Faculty' }],
roomIds:    [{ type: mongoose.Schema.Types.ObjectId, ref: 'Room' }]
```

Both default to empty arrays. Legacy Activity documents that predate S2.4 remain fully readable — Mongoose returns `[]` for missing array fields automatically. No data migration was required.

**Activity Service** (`server/core/institution/academic-context/activityService.js`)

- `getActivities()` — Extended to `.populate('facultyIds', 'name')` and `.populate('roomIds', 'name')` so the API returns resolved names, not raw ObjectIds.
- `createActivity()` — Logic unchanged. Return value now includes populated (empty) relationship arrays for consistency.
- `updateActivityRelationships(activityId, { facultyIds, roomIds })` — **New function.** Full validation pipeline:
  1. Validates `activityId` format (ObjectId).
  2. Resolves the current institution via the established single-tenant pattern.
  3. Confirms the Activity exists and belongs to the current institution.
  4. For each provided relationship field:
     - Validates array type.
     - Validates every element as a well-formed ObjectId.
     - Rejects duplicate identifiers within the array.
     - Queries the resource collection with both `_id: { $in: ids }` and `institutionId` to confirm existence **and** institutional ownership in a single query.
     - Rejects if the count of found records does not match the submitted count.
  5. Applies `$set` with only the provided fields — omitted fields are preserved.
  6. Returns the updated Activity with all relationships populated.

All validation runs to completion before any write occurs, preventing partial persistence on mixed valid/invalid input.

### 2.2 Backend — API Layer

**Activity Controller** (`server/controllers/activityController.js`)

Added `updateActivityRelationships` handler following the existing error-convention (`error.statusCode` → JSON `{ error }` response).

**Activity Routes** (`server/routes/activityRoutes.js`)

| Method | Path | Handler | Purpose |
|---|---|---|---|
| `GET` | `/api/activities` | `getActivities` | List all activities with populated relationships *(existing, extended)* |
| `POST` | `/api/activities` | `createActivity` | Create a new activity *(existing, unchanged)* |
| `PUT` | `/api/activities/:id/relationships` | `updateActivityRelationships` | **New.** Update faculty and/or room eligibility |

**Request/Response Contract — `PUT /api/activities/:id/relationships`**

| Aspect | Detail |
|---|---|
| **Body** | `{ facultyIds?: string[], roomIds?: string[] }` |
| **Success** | `200` `{ message: "Activity relationships updated successfully", activity: { ... } }` |
| **400 — Invalid Activity ID** | `{ error: "Invalid activity ID" }` |
| **400 — Invalid Faculty ID** | `{ error: "Invalid faculty ID format" }` |
| **400 — Invalid Room ID** | `{ error: "Invalid room ID format" }` |
| **400 — Non-array input** | `{ error: "facultyIds must be an array" }` or `"roomIds must be an array"` |
| **400 — Duplicates** | `{ error: "Duplicate faculty IDs are not allowed" }` or `"Duplicate room IDs..."` |
| **400 — Not found / cross-institution** | `{ error: "One or more faculty members not found or do not belong to this institution" }` |
| **400 — No fields** | `{ error: "No relationship fields provided for update" }` |
| **404 — Activity missing** | `{ error: "Activity not found" }` |

**Update Semantics:**

| Scenario | Behavior |
|---|---|
| `facultyIds` provided, `roomIds` omitted | Faculty list replaced; room list **preserved** |
| `roomIds` provided, `facultyIds` omitted | Room list replaced; faculty list **preserved** |
| Both provided | Both replaced independently |
| `facultyIds: []` | Faculty list **intentionally cleared**; rooms preserved |
| Neither provided | Rejected with `400` |

## 3. Relationship Storage Decision

**Decision: Embedded reference arrays on the Activity document.**

**Rationale:**

| Factor | Analysis |
|---|---|
| Ownership | Activity is the natural owner of its eligibility configuration |
| Access pattern | Relationships are always read and modified through an Activity |
| Query needs | No independent relationship queries required at this stage |
| Complexity | Two arrays on an existing document vs. two new collections, six new files, and join queries |
| Existing conventions | No relationship collections exist anywhere in the codebase |
| Scale | Eligibility lists per activity are small (tens, not thousands) |

**No ADR was required.** The embedded-array approach is the natural minimal fit for the current architecture. If future allocation requirements demand independent relationship lifecycle, metadata, or reverse queries (e.g., "which activities is Faculty X eligible for?"), a migration to a separate collection can be performed at that time with a documented ADR.

## 4. Problems Encountered and Mitigations

### 4.1 No Update Endpoint Existed

**Problem:** The S2.3 Activity API only exposed `GET /` (list) and `POST /` (create). There was no mechanism to modify an existing Activity, which is a prerequisite for relationship management.

**Mitigation:** Introduced `PUT /api/activities/:id/relationships` as a dedicated sub-resource endpoint rather than a generic `PATCH /api/activities/:id`. This keeps the semantics explicit — the endpoint manages eligibility only, not core Activity fields like `name` or `groupId`. If a general Activity update endpoint is needed in a future sprint, it can be added independently without ambiguity.

### 4.2 Single-Tenant Institution Pattern and Cross-Institution Testing

**Problem:** The codebase uses `Institution.findOne().sort({ createdAt: -1 })` to determine the "current" institution. This means cross-institution validation tests cannot simply create a second institution — they must ensure the correct institution is the most recently created one.

**Mitigation:** In the cross-institution test cases, after creating the "other" institution's resources, the original institution's `createdAt` is explicitly advanced (`new Date(Date.now() + 1000)`) to re-establish it as the active institution before attempting the invalid association. This mirrors the actual runtime behavior and tests the real validation path.

### 4.3 React `act()` Warning in Loading-State Test

**Problem:** The initial loading-state test rendered the component and asserted the loading message synchronously, but the mocked API promises resolved asynchronously after the assertion, causing React to emit `act()` warnings about unwrapped state updates.

**Mitigation:** Extended the test to `await waitFor(() => expect(screen.queryByText(/Loading.../)).not.toBeInTheDocument())`, which allows the component to complete its data-loading lifecycle within the test's `act()` boundary. All warnings are now eliminated.

### 4.4 Ensuring Independent Relationship Updates

**Problem:** A naive implementation using `findByIdAndUpdate` with the full document body could accidentally clear one relationship list when only the other was being updated.

**Mitigation:** The service constructs the `$set` update object dynamically — only fields explicitly present in the request body (checked via `!== undefined`) are included. An omitted field is never touched. This was verified with dedicated tests (faculty-only update preserves rooms, room-only update preserves faculty).

### 4.5 Atomic Validation Before Write

**Problem:** If a request contained a mix of valid and invalid resource IDs, a sequential validation approach could partially persist the valid ones before encountering the invalid one.

**Mitigation:** All validation (format, existence, institution, duplicates) runs to completion for **both** relationship fields before any `$set` is issued. The test "should not partially persist when one resource is valid and another is invalid" confirms this by asserting the Activity's `facultyIds` remains `[]` after a failed mixed update.
