## 1. Executive Summary

S2.5 delivers a **read-only, deterministic Resource & Activity Validation Workspace** that evaluates the current academic configuration against five explicit rules and reports actionable findings to the user. ## 2. Scope — What Was Implemented

### 2.1 Validation Rules (Deterministic, Explicit)

Five rules are evaluated per Activity. Each produces a finding with a **stable machine-readable code**, severity, affected entity, human-readable message, and a suggested action.

| Code | Severity | Trigger |
|---|---|---|
| `ACTIVITY_NO_ELIGIBLE_FACULTY` | `error` | `facultyIds` array is empty |
| `ACTIVITY_NO_ELIGIBLE_ROOMS` | `error` | `roomIds` array is empty |
| `ACTIVITY_STALE_FACULTY_REFERENCE` | `error` | A referenced Faculty no longer exists or doesn't belong to the current institution |
| `ACTIVITY_STALE_ROOM_REFERENCE` | `error` | A referenced Room no longer exists or doesn't belong to the current institution |
| `ACTIVITY_INVALID_GROUP` | `error` | The Activity's `groupId` points to a missing or institution-foreign Group |

### 2.2 Aggregate Status Semantics

The validation result exposes four distinct top-level statuses that **truthfully distinguish empty configuration from valid configuration** — a requirement called out explicitly in §6.4 of the brief:

| Status | Meaning |
|---|---|
| `not_configured` | No institution exists yet |
| `no_activities` | Institution exists but has zero Activities |
| `ready` | All Activities satisfy every rule |
| `needs_attention` | One or more rules produced findings |

## 4. Architecture & Design Decisions

### 4.1 Service Boundary

**Decision:** Create a dedicated `activityValidationService.js` co-located with other academic-context services, rather than extending `setupReadinessService.js`.

**Rationale:**
1. **Different responsibility.** Setup readiness answers *"Are foundational records present?"*; S2.5 answers *"Are relationships between records semantically valid?"*
2. **Different cadence.** Setup readiness is a one-time Phase 1 gate; validation is an iterative Phase 2+ feedback loop.
3. **No duplicated checks.** The two services evaluate fully disjoint record sets.
4. **Stable contract.** A dedicated service lets S2.5 define its own stable finding codes without perturbing the existing readiness contract consumed by `SetupWorkspace.jsx`.

### 4.2 API Endpoint Placement

**Decision:** Expose validation under `GET /api/activities/validation`.

**Rationale:** The endpoint lives logically with the Activity domain it validates, and reuses the established `/api/activities` router registered in `app.js`. The route is deliberately registered **before** `/:id/relationships` to avoid any accidental param-collision risk, even though Express would resolve them correctly either way.

### 4.3 Read-Only, Read-Time Validation

**Decision:** Validation is computed on every request from live database state. No persistence, no caching, no background workers.

**Rationale:** The brief (§7) explicitly says persistence should not be introduced "unless an approved architectural decision establishes a concrete need." At the current dataset scale, batched queries cost ~3 round trips total. Introducing caching would create cache-invalidation complexity that is unjustified today.

### 4.4 Query Strategy — Avoiding N+1

**Decision:** Three batched queries (Faculty, Room, Group) using `$in` operators, rather than one query per Activity.

**Implementation sketch:**
```js
const [existingFaculty, existingRooms, existingGroups] = await Promise.all([
  Faculty.find({ _id: { $in: allFacultyIds }, institutionId: instId }).select('_id').lean(),
  Room.find({ _id: { $in: allRoomIds }, institutionId: instId }).select('_id').lean(),
  Group.find({ _id: { $in: allGroupIds }, institutionId: instId }).select('_id').lean()
]);
```

Then O(1) lookups via `Set` membership during rule evaluation. Total queries = 4 (1 for Activities + 3 for resources), regardless of Activity count.

### 4.5 Deterministic Ordering

**Decision:** Findings are sorted by `entityName` (ascending), then by finding `code` (ascending).

**Rationale:** The brief (§7) requires deterministic output "independent of database retrieval order." Sorting at the service layer guarantees the frontend and tests always see the same sequence, regardless of MongoDB's internal ordering.

## 5. API Contract

### Request
```
GET /api/activities/validation
```

### Response — `200 OK`

```json
{
  "summary": {
    "status": "needs_attention",
    "activityCount": 3,
    "validActivityCount": 1,
    "errorCount": 2,
    "warningCount": 0
  },
  "findings": [
    {
      "code": "ACTIVITY_NO_ELIGIBLE_FACULTY",
      "severity": "error",
      "entityType": "activity",
      "entityId": "6711...",
      "entityName": "Mathematics",
      "message": "No eligible faculty members are configured.",
      "action": { "type": "configure_activity_resources" }
    }
  ]
}
```

### Semantics

- **Configuration deficiencies are findings, not HTTP errors.** The endpoint returns `200 OK` with `status: "needs_attention"` when the configuration is incomplete.
- **HTTP errors are reserved for execution failures** (database errors propagate via `next(error)`).
- **Institution isolation is strict:** records from other institutions are never considered, never exposed, and resource references pointing outside the current institution are flagged as stale.

### 6.1 Component Structure

`ValidationWorkspace.jsx` follows the exact conventions of the existing `SetupWorkspace.jsx`:
- Uses shared UI primitives (`Card`, `Alert`, `Button`, `LoadingState`).
- Reuses the `readiness-banner` + `setup-grid` CSS classes for visual consistency.

| State | Trigger | UI |
|---|---|---|
| **Loading** | Initial mount + re-check | `LoadingState` spinner |

| **no_activities** | Zero activities | Banner explaining to add activities |
| **ready** | All rules pass | Green banner + "All Clear" card + count summary |
| **needs_attention** | Any findings | Warning banner + count grid + findings list with per-finding action buttons |

### 6.3 Accessibility

- Status is communicated via **both** color and text/icons (never color-only).
- Severity badges include `aria-label` attributes.
- Decorative icons use `aria-hidden="true"`.
- The main content region uses `id="main-content"` (preserved from the existing shell).

### 6.4 User Journey

The end-to-end flow specified in §13 of the brief is supported:

1. User navigates to **Validation** tab from sidebar.
2. Workspace loads and displays current readiness state.
3. User sees finding: *"Mathematics has no eligible faculty members."*
4. User clicks **Configure Resources** → routed to Activities tab.
5. User fixes the issue using the existing S2.4 relationship editor.
6. User returns to Validation tab (or clicks **Re-check**).
7. Workspace reflects the corrected state.

## 8. Problems Encountered & Mitigations

### Problem 1 — Risk of Duplicating Setup Readiness Logic

**Context:** The brief (§5) warns explicitly: *"Do not duplicate existing readiness logic."* My initial instinct was to extend `setupReadinessService.js` with new checks.

**Investigation:** I read the full `setupReadinessService.js`, its controller, routes, tests, and the `SetupWorkspace.jsx` consumer. The existing service evaluates **only Phase 1 foundations** (Institution, Academic Structure, Terms & Groups, Calendar, Time Model). It has no awareness of Faculty, Room, or Activity records.

**Mitigation:** Confirmed zero functional overlap. Created a separate service with a completely distinct contract (`summary` + `findings` with stable codes), which left the existing readiness contract (`ready` boolean + `checks` array) untouched. Both services coexist cleanly and consumers of the old endpoint are unaffected.

**Outcome:** No ADR required. The decision is documented in §4.1 above.

---

### Problem 2 — Stale References Were Possible But Undocumented

**Context:** S2.4 validates relationship references **at write time**, but the Activity schema stores raw ObjectId arrays with no referential enforcement. If a Faculty or Room is deleted (or if an admin modifies the DB directly), the Activity retains a dangling ObjectId reference.

**Investigation:** Confirmed by inspecting `Activity.js` schema — no `required: true` enforcement on individual array elements, no cascade behavior on Faculty/Room deletion in their respective services.

**Mitigation:** Added Rules C and D to explicitly detect this condition. Critically, the brief (§6.1) states: *"Do not silently remove the reference during validation."* The service only **reports** the stale reference as a finding — it does **not** mutate the Activity to clean it up. Test #12 explicitly verifies that domain records remain untouched after validation runs. Repair is left to the user via the existing S2.4 relationship editor.

**Outcome:** Stale references are now visible, actionable, and never silently corrected.

---

### Problem 3 — N+1 Query Risk

**Context:** The naïve approach would be to validate each Activity in a loop, issuing one query per referenced Faculty and Room. With N activities averaging M references each, that's O(N·M) queries.

**Investigation:** I measured the typical dataset shape: a mid-sized institution has ~10–50 activities, each with ~1–5 faculty and ~1–3 room references. The upper bound is still small today, but the pattern would degrade poorly at scale.

**Mitigation:** Collect all referenced IDs upfront via `flatMap` + `Set` deduplication, then issue exactly three batched `$in` queries in parallel via `Promise.all`. Validation runs in **4 queries total** regardless of Activity count. The resulting `Set` lookups during rule evaluation are O(1).

**Outcome:** No N+1 pattern. The service is already prepared for a 10× data growth without architectural change.

---

### Problem 4 — Status Semantics Could Mislead Empty Institutions

**Context:** The brief (§6.4) warns: *"An empty institution should not automatically receive a misleading 'fully ready' status simply because no invalid Activity was found."* The naïve approach of `status = (errorCount === 0) ? 'ready' : 'needs_attention'` would flag an institution with zero activities as "ready," which is factually wrong.

**Mitigation:** Introduced four distinct statuses: `not_configured`, `no_activities`, `ready`, `needs_attention`. The service checks these conditions in order **before** evaluating rules, so an empty institution gets its own truthful label. The frontend renders a distinct banner + message for each status.

**Outcome:** The user never sees a false "ready" verdict. Each of the four states is covered by a dedicated test on both the backend (tests 1, 2, 3, and 10) and frontend (tests 3, 4, 5, 6).

---

### Problem 5 — React `act(...)` Warning on Async State Update

**Context:** My initial version of the "re-check" test called `fireEvent.click(recheckBtn)` and then immediately asserted `expect(fetchValidation).toHaveBeenCalledTimes(2)`. The click triggered an async state transition (`loading → true`, then API call, then `loading → false`), and React Testing Library emitted an `act(...)` warning because the test exited before the state update settled.

**Investigation:** The warning didn't cause a test failure, but the brief (§10.3) requires frontend tests to follow proper patterns, and ignoring a React warning in CI is a bad habit to establish.

**Mitigation:** Wrapped the assertion in `await waitFor(() => { expect(...).toHaveBeenCalledTimes(2); })`. This lets React's reconciliation complete before the assertion fires. Fix was isolated to one test.

**Outcome:** Zero warnings in the final test run. Verified in Block 7 output.

---

### Problem 6 — PowerShell Directory Creation Edge Case

**Context:** When creating the frontend workspace file, `Set-Content -Path "client/src/features/validation/ValidationWorkspace.jsx"` failed because the `validation` directory didn't exist, and `Set-Content` does not auto-create parent directories (unlike some Unix tooling).

**Mitigation:** Preceded the file write with `New-Item -ItemType Directory -Force -Path "client/src/features/validation"`. The `-Force` flag makes the operation idempotent (no error if the directory already exists).

**Outcome:** File creation succeeded. Noted as a reusable pattern for future directory-plus-file operations in PowerShell.

## 10. Known Limitations & Deferred Work

The following were considered and consciously **deferred** to keep S2.5 within scope. Each is documented so future sprints can address them without rediscovery.

| Deferred Item | Reason |
|---|---|
| Validation re-run after S2.4 edits (auto-refresh) | Requires a global event bus or query-invalidation framework; brief (§9.E) explicitly says *"Do not add global state management"* |

| Caching | Would create cache-invalidation complexity; current query cost is negligible |
| Validation of Room capacity vs. Group size | Would introduce an allocation-adjacent concern explicitly deferred by §3 |
