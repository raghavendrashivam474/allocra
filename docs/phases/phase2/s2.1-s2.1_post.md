## 3. S2.1 — Faculty Foundation: What Was Implemented

### 3.1 Domain Model (`server/data/models/Faculty.js`)

A minimal Mongoose schema representing a faculty member:

- `institutionId` — ObjectId ref to `Institution`, required
- `departmentId` — ObjectId ref to `Department`, required
- `name` — String, required, trimmed
- `createdAt` — Date, auto-populated

The model mirrors the existing `Program.js` structure exactly, maintaining consistency with the established `institutionId` + parent-reference pattern.

### 3.2 Domain Service (`server/core/institution/resources/faculty/facultyService.js`)

Two exported functions:

- **`getFaculty()`** — Resolves the active institution, returns all faculty members with populated `departmentId` (name only), sorted by creation date.
- **`createFaculty({ departmentId, name })`** — Validates department existence, verifies the department belongs to the active institution (preventing cross-institution assignment), normalizes the name, and persists the record with the institution context derived server-side.

The service throws errors with `error.statusCode` properties (400/404), matching the existing convention established by `programService.js`.

### 3.3 Controller and Routes

- **`GET /api/faculty`** — Returns `{ faculty: [...] }`
- **`POST /api/faculty`** — Accepts `{ departmentId, name }`, returns 201 with `{ message, faculty }`

Route mounted in `server/app.js` at `/api/faculty`.

### 3.4 Frontend

- **API Client** (`client/src/api/faculty.js`) — `fetchFaculty()` and `createFaculty(data)` following the existing fetch-with-error-parsing pattern.
- **View** (`client/src/features/faculty/FacultyView.jsx`) — Full CRUD configuration screen with:
  - Institution guard (redirects to error if institution not configured)
  - Loading state via `LoadingState` primitive
  - Empty state via `EmptyState` primitive with action button
  - Inline creation form with department dropdown and name input
  - Faculty list displaying name and associated department
- **Navigation** — Added under a new "Resources" section in the application sidebar.

### 3.5 Tests

- **Backend** (`server/tests/faculty.test.js`, 10 tests):

## 4. S2.2 — Rooms and Physical Resources: What Was Implemented

### 4.1 Domain Model (`server/data/models/Room.js`)

- `institutionId` — ObjectId ref to `Institution`, required
- `name` — String, required, trimmed
- `type` — String, enum-controlled (`Classroom`, `Laboratory`, `Seminar Room`, `Auditorium`, `Other`), defaults to `Classroom`
- `capacity` — Number, required, minimum 1
- `createdAt` — Date, auto-populated
- **Composite unique index** on `{ institutionId, name }` to prevent duplicate room names within an institution

The `ROOM_TYPES` array is exported from the model for use by the service and controller.

### 4.2 Domain Service (`server/core/institution/resources/rooms/roomService.js`)

Two exported functions:

- **`getRooms()`** — Resolves active institution, returns all rooms sorted by creation date.
- **`createRoom({ name, type, capacity })`** — Validates name (required, trimmed), type (must be in `ROOM_TYPES`), capacity (must be a positive integer), checks for duplicate names within the institution (case-insensitive), and persists with server-derived institution context.

### 4.3 Controller and Routes

- **`GET /api/rooms`** — Returns `{ rooms: [...], roomTypes: [...] }` (the `roomTypes` array enables the frontend to dynamically populate the type dropdown)
- **`POST /api/rooms`** — Accepts `{ name, type, capacity }`, returns 201 with `{ message, room }`

Route mounted in `server/app.js` at `/api/rooms`.

### 4.4 Frontend

- **API Client** (`client/src/api/rooms.js`) — `fetchRooms()` and `createRoom(data)`.
- **View** (`client/src/features/rooms/RoomsView.jsx`) — Configuration screen with:

  - Loading and empty states using existing primitives
  - Creation form with name input, type dropdown (populated from API), and capacity number input
  - Room list displaying name, type badge, and capacity
- **Navigation** — Added as "Rooms" under the "Resources" sidebar section alongside Faculty.

### 4.5 Tests

## 5. Problems Encountered and Mitigations

### Problem 1: Incorrect Relative Import Path in Faculty Service

**Symptom:** All 10 server test suites failed simultaneously with `Cannot find module '../../../data/models/Faculty.js'`.

**Root Cause:** The `facultyService.js` file resides at `server/core/institution/resources/faculty/`, which is **four** directory levels below `server/`. The initial import used three levels (`../../../data/models/`), which resolved to `server/core/data/models/` — a nonexistent path.

**Mitigation:** Corrected the import to `../../../../data/models/Faculty.js` (four levels). This was caught immediately because the full test suite was run before proceeding.

**Lesson:** The existing Phase 1 services live at `server/core/institution/<domain>/` (three levels deep). The new `resources/<domain>/` nesting adds an extra level. Future Phase 2 services under `resources/` must use four-level relative paths.

---

### Problem 2: EmptyState Component Prop Mismatch

**Symptom:** The Faculty frontend test `renders empty faculty list with EmptyState when departments exist` failed. The rendered HTML showed an empty `<p>` tag inside the `empty-state` div — the text "No faculty members yet" was not appearing.

**Root Cause:** The initial `FacultyView.jsx` passed `title` and `description` props to `<EmptyState>`, but the actual `EmptyState` primitive (inspected at `client/src/components/ui/EmptyState.jsx`) accepts `message`, `actionLabel`, `onAction`, `actionDisabled`, and `className`. The `title` and `description` props were silently ignored.

**Mitigation:** Rewrote the `EmptyState` usage to pass the correct `message` prop and leveraged `actionLabel`/`onAction` for the inline "Add Faculty Member" button. Updated the test assertions to match the actual rendered text.

**Lesson:** Always inspect the actual primitive component's prop interface before composing it. Do not assume prop names from documentation or convention.

---

### Problem 3: Malformed JSX in App.jsx After Regex Replacement

**Symptom:** After using PowerShell `-replace` to inject the Faculty navigation button, the `className` attribute was rendered as `className={"allocra-nav-item \"}` — a broken template literal with an escaped quote.

**Root Cause:** The PowerShell regex replacement string contained nested backticks and dollar signs that conflicted with PowerShell's string interpolation and JSX template literal syntax. The `$` in `${activeTab}` was being consumed by PowerShell's variable expansion.

**Mitigation:** Rewrote the entire `App.jsx` file cleanly using a PowerShell here-string (`@' ... '@`), which treats all content literally. This eliminated all escaping ambiguities.

**Lesson:** Regex-based patching of JSX/TSX files via PowerShell is fragile. For files with template literals, prefer full-file rewrites using single-quoted here-strings.

---

### Problem 4: PowerShell String Parsing Failures During Documentation Updates

**Symptom:** Multiple attempts to patch `docs/architecture.md` and `README.md` using `-replace` with markdown content containing `**` (bold) and backtick (code) characters caused PowerShell parser errors: `"You must provide a value expression following the '-' operator"` and `"Unexpected token 'Calendar**:'"`.

**Root Cause:** In PowerShell, the backtick is the escape character, and `**` inside double-quoted strings triggers operator parsing. The markdown content `- **Calendar**: \`institutionId\`` was being interpreted as a series of PowerShell operators rather than a literal string.

**Mitigation:** Switched to `[System.IO.File]::ReadAllText()` and `.Replace()` (the .NET string method, not PowerShell's `-replace` operator) combined with single-quoted strings for the search text. This bypasses all PowerShell parsing entirely.

**Lesson:** When manipulating files containing markdown, code, or special characters via PowerShell, use .NET file I/O methods and single-quoted strings exclusively.

## 6. Architecture Decisions

| Decision | Rationale |
|---|---|
| Faculty and Room are separate models, not a unified `Resource` base | They have fundamentally different semantics (person+department vs. space+capacity+type). Premature unification would create a leaky abstraction. Per brief Section 35. |
| Room type uses a controlled enum, not a free-text field | Future allocation logic will need to reason about room types (e.g., "labs can only host lab activities"). A controlled vocabulary prevents data quality issues. |
| Room name uniqueness is scoped to institution, not global | Multi-institution support may arrive later. Global uniqueness would be an unnecessary constraint. |
| `GET /api/rooms` returns `roomTypes` alongside `rooms` | Enables the frontend to dynamically populate the type dropdown without hardcoding the enum in two places. |
| No `PUT`/`DELETE` endpoints for Faculty or Room | The brief explicitly stated to implement only the minimum API necessary. These can be added when the product requires editing or removal. |
| Institution resolution continues using `Institution.findOne().sort({createdAt:-1})` | The existing pattern works correctly. The brief's Section 36 states not to introduce a new resolver unless it becomes a genuine maintenance problem. |
