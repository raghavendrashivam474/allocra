# S3.1 — Allocation Domain Contract

**Project:** Allocra
**Phase:** Phase 3 — Allocation Core
**Sprint:** S3.1
**Baseline:** `v-UX-0` (commit `0f80017`)
**Status:** Established

---

## 1. Definition

> An **Allocation** represents the assignment of an existing academic Activity
> to a single specific eligible Faculty member and a single specific eligible
> Room within the same institution context.

### Rationale

| Question | Answer | Evidence |
|---|---|---|
| Is one Allocation a single Activity–Faculty–Room assignment? | **Yes.** 1:1:1. | Activity already carries `groupId` and `institutionId`; no separate references needed. |
| Can one Activity have multiple Allocations? | **Yes.** | A course may be taught by different faculty in different rooms (e.g., multiple sections). |
| Can an Allocation have multiple Faculty or Rooms? | **No.** | Each allocation is one specific assignment. Multiple assignments = multiple Allocations. |
| Is Group already represented by the Activity? | **Yes.** | `Activity.groupId` is required. Allocation inherits it. No separate Group reference. |
| Does the domain require a session or occurrence identity? | **Not yet.** | No time-slot, calendar-period, or recurrence semantics exist in the current models. |
| Is an allocation meaningful before a date or time is assigned? | **Yes, for resource assignment.** | The current domain supports "who teaches this, where" without scheduling. Time is a future concern. |
| Can an allocation exist as a draft? | **Not yet.** | No product requirement justifies lifecycle states in S3.1. |
| What does an allocation's existence mean? | **A confirmed resource commitment.** | It means "this faculty member is assigned to teach this activity in this room." |

## 2. Entity Relationships & Cardinality

```text
Institution (1) ──< Activity (1) ──< Allocation (many)
│ │
│ ├──> Faculty (1)
│ └──> Room (1)
│
├──> Group (1) [inherited by Allocation via Activity]
├──> Faculty (many) [eligibility pool]
└──> Room (many) [eligibility pool]
```

| Relationship | Cardinality | Notes |
|---|---|---|
| Activity → Allocations | 1 : many | One activity can have multiple allocations |
| Allocation → Activity | many : 1 | Each allocation references exactly one activity |
| Allocation → Faculty | many : 1 | Each allocation assigns exactly one faculty member |
| Allocation → Room | many : 1 | Each allocation assigns exactly one room |
| Allocation → Group | derived | Via `activity.groupId`; not stored on Allocation |
| Allocation → Institution | derived | Via `activity.institutionId`; not stored on Allocation |

---

## 3. Identity & Uniqueness

### Identity
Each Allocation has its own unique identifier (`_id` when persisted). The Activity reference alone is insufficient because one Activity can have multiple Allocations.

### Uniqueness Rule
**The tuple `(activityId, facultyId, roomId)` must be unique.**

**Domain justification:** Assigning the same faculty member to the same activity in the same room more than once has no academic meaning without time/session semantics. Duplicate tuples indicate a user error, not a valid scenario.

**Re-evaluation trigger:** When time or session semantics are introduced (future sprint), this rule will need to be revisited. At that point, the uniqueness key would likely expand to include a session or occurrence identifier.

---

## 4. Institution Ownership Invariants

| Rule | Enforcement |
|---|---|
| The Activity must belong to the current institution | State-dependent (persistence layer) |
| The Faculty must belong to the current institution | State-dependent (persistence layer) |
| The Room must belong to the current institution | State-dependent (persistence layer) |
| Client-supplied institution identifiers must not be trusted | Use `Institution.findOne().sort({ createdAt: -1 })` |
| Cross-institution combinations must be rejected | All three entities must resolve to the same institution |

---

## 5. Eligibility Invariants

| Rule | Meaning |
|---|---|
| `facultyId` must be present in `activity.facultyIds` | The assigned faculty member must be in the eligibility pool configured via S2.4 |
| `roomId` must be present in `activity.roomIds` | The assigned room must be in the eligibility pool configured via S2.4 |
| Empty eligibility pools block allocation | If `activity.facultyIds` is empty, no faculty allocation is valid. Same for rooms. |
| Stale eligibility references block allocation | If a referenced Faculty or Room no longer exists (detected by S2.5 validation), allocation using that reference is invalid |

**Key distinction:** Eligibility (S2.4) defines *who can* and *where it can*. Allocation (S3.1) is the *specific choice* from those sets. Allocation must never bypass eligibility.

---

## 6. Lifecycle

**Decision: No lifecycle states in S3.1.**

**Rationale:** The current product requirements do not describe draft, proposed, confirmed, or cancelled allocation states. An allocation either exists (confirmed resource assignment) or does not. Introducing status fields without a product requirement would violate the brief's instruction: *"Do not introduce status fields merely to make the model look complete."*

**Re-evaluation trigger:** If future sprints introduce approval workflows, tentative assignments, or cancellation tracking, lifecycle states should be added with a documented ADR.

## 7. Domain Errors

### Pure Validation Errors (shape and format — no database access)

| Code | Condition |
|---|---|
| `ALLOCATION_INVALID_ACTIVITY_ID` | `activityId` is not a valid ObjectId format |
| `ALLOCATION_INVALID_FACULTY_ID` | `facultyId` is not a valid ObjectId format |
| `ALLOCATION_INVALID_ROOM_ID` | `roomId` is not a valid ObjectId format |
| `ALLOCATION_MISSING_ACTIVITY_ID` | `activityId` is absent or null |
| `ALLOCATION_MISSING_FACULTY_ID` | `facultyId` is absent or null |
| `ALLOCATION_MISSING_ROOM_ID` | `roomId` is absent or null |

### State-Dependent Errors (require database context — enforced at persistence)

| Code | Condition |
|---|---|
| `ALLOCATION_ACTIVITY_NOT_FOUND` | Activity does not exist in the current institution |
| `ALLOCATION_FACULTY_NOT_FOUND` | Faculty does not exist in the current institution |
| `ALLOCATION_ROOM_NOT_FOUND` | Room does not exist in the current institution |
| `ALLOCATION_FACULTY_NOT_ELIGIBLE` | Faculty exists but is not in `activity.facultyIds` |
| `ALLOCATION_ROOM_NOT_ELIGIBLE` | Room exists but is not in `activity.roomIds` |
| `ALLOCATION_CROSS_INSTITUTION` | Referenced entities belong to different institutions |
| `ALLOCATION_DUPLICATE` | An allocation with the same `(activityId, facultyId, roomId)` already exists |
| `ALLOCATION_INSTITUTION_NOT_CONFIGURED` | No institution exists yet |

## 8. Explicitly Deferred Concepts

| Concept | Reason |
|---|---|
| Time-slot / session / occurrence | No time model fields exist on Activity or any related entity |
| Conflict detection (room overlap, faculty double-booking) | Requires scheduling semantics that don't exist yet |
| Room capacity vs. Group size | Explicitly deferred by S2.5 §10; no product rule yet |
| Lifecycle states (draft, confirmed, cancelled) | No product requirement |
| Bulk allocation | No UI or API requirement |
| Allocation history / audit trail | No product requirement |
| Recurring allocations | No recurrence model |
| Priority or preference metadata | No product requirement |

## 9. Compatibility with Phase 2

| Phase 2 Contract | Impact |
|---|---|
| Activity schema (`facultyIds`, `roomIds`) | **Unchanged.** Allocation reads eligibility; does not modify it. |
| S2.4 relationship updates | **Unchanged.** Eligibility management remains the coordinator's responsibility. |
| S2.5 validation service | **Unchanged.** Validation continues to evaluate configuration readiness independently. |
| Institution resolution pattern | **Reused.** Same `Institution.findOne().sort({ createdAt: -1 })` convention. |
| Error handling convention | **Reused.** Same `error.statusCode` + `error.message` pattern. |
| Existing APIs | **Unchanged.** No existing endpoints are modified. |

## 10. Open Questions

| Question | Status | Notes |
|---|---|---|
| Should allocation enforce that the Activity's validation status is `ready` before allowing assignment? | **Deferred** | Plausible but not required. A coordinator may want to allocate partial resources while fixing other issues. |
| Should deleting a Faculty or Room cascade to remove related Allocations? | **Deferred** | Requires persistence layer (S3.2). Current models have no cascade behavior. |
| Should allocation support "unassigned" states (e.g., faculty assigned but room TBD)? | **Deferred** | Current definition requires all three references. Partial allocation could be a future lifecycle concept. |
