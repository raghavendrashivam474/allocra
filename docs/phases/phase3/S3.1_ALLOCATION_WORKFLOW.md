# S3.1 — Allocation Workflow Specification

**Project:** Allocra
**Sprint:** S3.1
**Baseline:** `v-UX-0` (commit `0f80017`)
**Status:** Specification for S3.3 Implementation

---

## 1. Entry Point

The allocation workspace will be accessible as a new tab in the existing
sidebar navigation (alongside Setup, Activities, Validation, etc.).

**Tab label:** "Allocations"
**Route:** Internal tab switch via the existing `onNavigate` prop pattern
**Prerequisite:** Institution must be configured and at least one Activity
must exist with non-empty eligibility lists.

---

## 2. Coordinator Journey

### Step 1 — Open the Allocation Workspace
- Coordinator clicks "Allocations" in the sidebar.
- The workspace loads the list of Activities that have at least one eligible
  faculty member AND at least one eligible room.
- Activities with empty eligibility pools are shown in a separate
  "Not Ready" section with a link to the Validation Workspace.

### Step 2 — View Allocation Context
- For each allocatable Activity, the workspace displays:
  - Activity name and parent Group name
  - Count of eligible faculty (from `activity.facultyIds`)
  - Count of eligible rooms (from `activity.roomIds`)
  - Count of existing allocations (if any, from S3.2+)
  - Current allocation assignments (Faculty name + Room name)

### Step 3 — Create an Allocation
- Coordinator clicks "Allocate" on an Activity card.
- A focused assignment panel opens showing:
  - Dropdown or selection list of eligible Faculty (from `activity.facultyIds`)
  - Dropdown or selection list of eligible Rooms (from `activity.roomIds`)
  - Only eligible resources are shown — ineligible resources are excluded
  - A "Confirm Allocation" button
- Coordinator selects one Faculty and one Room, then confirms.

### Step 4 — Validation Feedback
- If the assignment is valid, the allocation is created and the card updates
  to show the new assignment.
- If the assignment is invalid (e.g., duplicate tuple), the workspace shows
  a clear error message using the domain error codes:
  - "This faculty member is already assigned to this activity in this room."
  - "The selected faculty member is no longer eligible for this activity."
- The error message includes the violated rule and a suggested action.

### Step 5 — Review and Verify
- Coordinator can see all current allocations at a glance.
- Each allocation shows: Activity name, Faculty name, Room name.
- Coordinator can remove an allocation if needed (future S3.3 action).

---

## 3. Valid and Blocked States

| State | Condition | UI Behavior |
|---|---|---|
| **No institution** | Institution not configured | Banner: "Configure your institution first" + link to Setup |
| **No activities** | Zero activities exist | Banner: "Add activities before creating allocations" + link to Activities |
| **No eligible activities** | Activities exist but none have both faculty and room eligibility | Banner: "Configure eligible resources for your activities" + link to Validation |
| **Ready to allocate** | At least one activity has non-empty faculty AND room pools | Show allocatable activity cards with "Allocate" action |
| **Allocation complete** | Allocation successfully created | Success feedback + updated card showing the assignment |
| **Allocation blocked** | Validation error (duplicate, ineligible, stale ref) | Error feedback with specific reason and suggested action |

---

## 4. Loading, Empty, Error, and Success Behavior

| Scenario | Behavior |
|---|---|
| **Loading** | Show `LoadingState` spinner (existing UI primitive) |
| **Empty** | Show `EmptyState` with contextual message and navigation link |
| **API Error** | Show `Alert` with error message and "Retry" button |
| **Success** | Show `Alert` with success message (auto-dismiss after 1.2s, matching S2.4 pattern) |
| **Validation Error** | Show inline error on the assignment panel with the specific domain error message |

---

## 5. Faculty Journey (Future — Not Implemented in S3.1)

Once authentication and schedule publication exist (future Phase 3+ sprints):

- Faculty members will see a read-only personal view.
- The view will display their allocated activities, assigned rooms, and
  group context.
- Faculty will NOT be able to create, modify, or delete allocations.
- Faculty will NOT see allocations belonging to other faculty members.

**Current status:** No faculty-facing allocation UI exists. Do not fabricate
mock faculty dashboards or schedule views. The UX Contract (§2.B) explicitly
prohibits this until identity and allocation APIs exist.

## 6. Dependencies on Future Sprints

| Dependency | Sprint | What It Provides |
|---|---|---|
| Allocation persistence (model, collection) | S3.2 | Database storage for allocations |
| State-dependent validation (existence, eligibility, institution) | S3.2 | Full validation beyond pure format checks |

| Allocation workspace frontend component | S3.3 | The actual UI described in this specification |

---

## 7. UX Contract Compliance

| Principle | How This Workflow Complies |
|---|---|
| **Action over Navigation** | "Allocate" button is directly on the Activity card; no sub-menu navigation |
| **Context over Memorization** | Eligibility counts and group names shown alongside each Activity |
| **Guided when Needed** | Empty states guide coordinators to Setup or Validation first |
| **Prevention over Correction** | Only eligible resources are shown in the selection lists |
| **Honest System State** | No mock data; allocations reflect actual database state |
| **Progressive Complexity** | Simple card-based view; no advanced filtering until needed |
