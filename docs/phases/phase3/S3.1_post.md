## 5. Domain Decisions & Rationale

This section is the heart of the sprint. Each decision below was taken deliberately and recorded in the Allocation Domain Contract.

### 5.1 Allocation Definition

> **An Allocation represents the assignment of an existing academic Activity to a single specific eligible Faculty member and a single specific eligible Room within the same institution context.**

Cardinality: **1 Activity : 1 Faculty : 1 Room** per allocation.

**Why this granularity:**

- The existing Activity schema is the natural unit of academic work. It already carries `groupId` and `institutionId`.
- Multiple faculty teaching the same activity is modeled as **multiple allocations**, not one allocation with multiple faculty. This keeps the data model simple and makes future audit/history work straightforward.
- Multiple rooms (e.g., same session held in two rooms simultaneously) is a specialized scenario that is not required by any current product need and is better modeled through multiple allocations if it ever arises.

**Alternatives considered and rejected:**

| Alternative | Why rejected |
|---|---|
| Allocation holds arrays of `facultyIds` and `roomIds` | Duplicates the eligibility model from Activity; blurs the eligibility-vs-assignment boundary; makes uniqueness and conflict reasoning harder in future sprints |
| Allocation references only Activity and Faculty (room assigned later) | Introduces an implicit draft/partial state without a product requirement for lifecycle |

### 5.2 Identity & Uniqueness

- Each Allocation has its own `_id` (when persisted in S3.2). Activity reference alone is not sufficient as a key, because one Activity can legitimately have many allocations.
- **Uniqueness rule:** the tuple `(activityId, facultyId, roomId)` must be unique.

**Why this specific tuple:** Without time or session semantics, assigning the same faculty member to the same activity in the same room more than once has no academic meaning. Allowing it would represent user error, not a valid scenario. When time/session semantics are eventually introduced, this rule will need re-evaluation — likely by extending the uniqueness key to include a session identifier.

### 5.3 Institution Ownership

An Allocation does **not** store `institutionId` directly. Instead:

- The Activity owns `institutionId`.
- The Allocation inherits institution context via its Activity reference.
- All three references (Activity, Faculty, Room) must resolve to the same institution — this becomes a state-dependent validation check in S3.2.
- Client-supplied institution identifiers are never trusted; the authoritative institution is resolved via the existing `Institution.findOne().sort({ createdAt: -1 })` pattern.

### 5.4 Eligibility

- `facultyId` must be present in `activity.facultyIds` (eligibility pool from S2.4).
- `roomId` must be present in `activity.roomIds` (eligibility pool from S2.4).
- An activity with an empty eligibility pool cannot have allocations referencing that pool.
- Stale eligibility references (already detected by S2.5 validation) block allocation.

**Key boundary clarification:** Eligibility (S2.4) answers *"who can teach this, where can it be held"*. Allocation (S3.1) answers *"who is teaching this, where is it being held"*. Allocation must never bypass eligibility — a faculty member must first be eligible before they can be allocated.

### 5.5 Lifecycle

**Decision: No lifecycle states in S3.1.**

The brief (§5.A3) is explicit: *"If the current product requirements do not require a lifecycle, keep the contract minimal. Do not introduce status fields merely to make the model look complete."*

No current product requirement describes draft, proposed, confirmed, cancelled, or any other allocation state. An allocation either exists (confirmed resource commitment) or does not. If future workflows (approvals, tentative holds, cancellation history) require states, they will be added via an ADR at that time.

### 5.6 Error Taxonomy

Fourteen stable error codes were defined, split into two categories:

**Pure validation errors (6)** — enforceable without database access, implemented in S3.1:

- `ALLOCATION_MISSING_ACTIVITY_ID`
- `ALLOCATION_MISSING_FACULTY_ID`
- `ALLOCATION_MISSING_ROOM_ID`
- `ALLOCATION_INVALID_ACTIVITY_ID`
- `ALLOCATION_INVALID_FACULTY_ID`
- `ALLOCATION_INVALID_ROOM_ID`

**State-dependent errors (8)** — require database context, specified for S3.2:

- `ALLOCATION_ACTIVITY_NOT_FOUND`
- `ALLOCATION_FACULTY_NOT_FOUND`
- `ALLOCATION_ROOM_NOT_FOUND`
- `ALLOCATION_FACULTY_NOT_ELIGIBLE`
- `ALLOCATION_ROOM_NOT_ELIGIBLE`
- `ALLOCATION_CROSS_INSTITUTION`
- `ALLOCATION_DUPLICATE`
- `ALLOCATION_INSTITUTION_NOT_CONFIGURED`

Each error carries a `code`, `field`, and `message`. The split is important because it preserves the brief's distinction (§6.B2) between validation that works without a database and validation that cannot.

### 5.7 Explicitly Deferred Concepts

| Concept | Why deferred |
|---|---|
| Time-slot, session, occurrence | No time model exists on Activity or any related entity |
| Conflict detection (room overlap, faculty double-booking) | Requires scheduling semantics that don't exist yet |
| Room capacity vs. Group size | Already deferred by S2.5 §10; no product rule exists |
| Lifecycle states | No product requirement |
| Bulk allocation | No UI or API requirement |
| Allocation history / audit trail | No product requirement |
| Recurring allocations | No recurrence model |
| Priority or preference metadata | No product requirement |

## 6. Implementation

### 6.1 Pure Validation Module

**File:** `server/core/institution/academic-context/allocationValidationService.js`

**Public API:**

```javascript
import {
  validateAllocationInput,
  ALLOCATION_ERRORS
} from './allocationValidationService.js';

const result = validateAllocationInput({ activityId, facultyId, roomId });
// → { valid: true }
// → { valid: false, errors: [{ code, field, message }, ...] }
```

**Design properties:**

| Property | Implementation |
|---|---|
| Pure | No database access, no network, no filesystem, no side effects |
| Deterministic | Same input always produces the same output |
| Non-throwing | Always returns a result object; never throws |
| Collects all errors | Does not short-circuit; reports every violation in one pass |
| Guards against bad input shapes | Handles `null`, `undefined`, non-object input |
| Follows project conventions | Same file location pattern as `activityValidationService.js`; ESM; mongoose dependency already in project |

**Why no new dependency:** The brief (§6.B1) is explicit: *"Do not introduce TypeScript, Zod, Joi, a validation library, or a new domain package solely for this sprint."* The validator uses only `mongoose.Types.ObjectId.isValid()`, which is already imported throughout the codebase.

## 7. Problems Encountered & Mitigations

This sprint was unusual in that most of the work was **not** writing code — it was resolving domain questions correctly without inventing product requirements. The problems below reflect that reality.

### 7.1 Problem — Risk of Conflating Eligibility with Allocation

**Context:** S2.4 stores `facultyIds` and `roomIds` on the Activity document. On the surface, these look like allocations. A junior developer could easily have assumed that "allocation" simply means "pick one from each list" — and then built a feature that modifies these arrays, blurring the eligibility boundary that S2.4 explicitly established.

**Investigation:** I re-read the S2.4 completion report line by line. Section 1 states: *"The implementation is a pure eligibility registry, ready to support S2.5 validation and the later Phase 3 allocation engine."* Section 2.1 reinforces: eligibility is *"explicitly a configuration layer"*, distinct from the allocation engine. The UX Contract (§2.A) also treats "Configure Resources" (eligibility) and allocation as separate journeys.

**Mitigation:** The Allocation Domain Contract treats eligibility as a **read-only input constraint**, not a storage target. S3.1 does not propose any writes to `activity.facultyIds` or `activity.roomIds`. The domain contract (§5) explicitly states the boundary: *"Allocation must never bypass eligibility."* The validation implementation does not touch Activity documents at all.

**Outcome:** The eligibility/allocation boundary is now documented as a first-class invariant. S3.2 and S3.3 cannot accidentally violate it without reversing an explicit decision.

---

### 7.2 Problem — Pressure to Introduce Time Semantics

**Context:** The intuitive expectation when hearing "allocation" is that it includes a time slot (date, period, day-of-week). Every other scheduling product in the market does this. The temptation to add a `date` or `periodId` field was real, especially since Phase 1 produced a `TimeModel` schema.

**Investigation:** I inspected the actual Activity, Group, Faculty, and Room models. None of them carry any time field. The `TimeModel` collection exists but is not referenced by Activity. There is no product requirement document that specifies how allocations relate to time, no recurrence rule, no calendar overlay for allocations, and no mention in the UX Contract of time-based allocation views.

**Mitigation:** The brief (§3) explicitly excludes *"time-slot, session, recurrence, or calendar semantics that have not been established."* I honored this exclusion. The domain contract (§8) lists time-slot semantics as an **explicitly deferred concept** with a clear reason: *"No time model fields exist on Activity or any related entity."* The contract also notes (§3) that the uniqueness rule will need re-evaluation when time semantics are eventually introduced.

**Outcome:** No time fields were introduced. The contract clearly flags this as future work. The deferral is reversible with an ADR when a product requirement arises.

---

### 7.3 Problem — Pressure to Introduce Lifecycle States

**Context:** Modern web applications often have status fields (`draft`, `published`, `archived`). It would have been easy to add a `status: 'confirmed'` field "just in case" the product later needs it.

**Investigation:** I reviewed the brief (§5.A3), the UX Contract, and the S2.4/S2.5 reports. No product requirement describes draft, proposed, confirmed, or cancelled allocation states. The brief is explicit: *"Do not introduce status fields merely to make the model look complete."*

**Mitigation:** The domain contract (§6) records the decision not to introduce lifecycle states, with a clear re-evaluation trigger: *"If future sprints introduce approval workflows, tentative assignments, or cancellation tracking, lifecycle states should be added with a documented ADR."* The pure validator does not check status, the error codes do not include state-transition errors, and the workflow specification does not depict state transitions.

**Outcome:** The model stays minimal. Future lifecycle work will be deliberate, product-driven, and ADR-documented rather than accidental and ambient.

---

### 7.4 Problem — Deciding Where Validation Belongs

**Context:** The brief (§6.B2) requires a clear separation between **pure validation** (shape, format) and **state-dependent validation** (existence, eligibility, institution ownership). But S3.2 doesn't exist yet. There was a temptation to either (a) implement state-dependent checks with a mock database stub, or (b) implement nothing until S3.2.

**Investigation:** Option (a) would couple the pure validator to a test harness and risk pretending we have working allocation CRUD. Option (b) would leave the sprint without a testable implementation foundation, violating §6 of the brief.

**Mitigation:** The validation module is strictly pure. It validates ObjectId format and presence. It does not import any model, does not perform any query, and does not know about institutions, eligibility, or persistence. State-dependent validation is specified in the domain contract (§7) and in the handoff to S3.2, with the required checks, error codes, and institution resolution pattern already defined. S3.2 will add a second validation stage that calls the pure validator first, then performs state-dependent checks.

**Outcome:** The pure validator is independently testable without any database. S3.2 inherits a clear foundation and does not have to re-invent either the error codes or the checking order.

---

### 7.5 Problem — PowerShell Here-String Formatting Artifacts

**Context:** During document creation, PowerShell `@"..."@` here-strings produced some rendering artifacts in the terminal (visible as `␦`, `\x0a`, and escaped backticks) because of how the terminal transmitted the content for display. This was purely a terminal-display issue, not a file-content issue — but it was alarming at first glance.

**Investigation:** I ran `Test-Path` on each generated file after creation. All three documentation files were confirmed to exist. The file contents themselves are correctly encoded UTF-8 markdown; the display artifacts appeared only in the PowerShell transcript, not in the on-disk files. This is a known behavior when very long here-strings interact with certain terminal buffer configurations.

**Mitigation:** For this report I am providing the content directly rather than via a PowerShell block, so there is no transcription layer to introduce artifacts. The on-disk documents remain correctly formatted. A future improvement for sprint tooling would be to use `[System.IO.File]::WriteAllText(...)` with an explicit UTF-8 encoding object, which avoids PowerShell's default BOM/newline handling for long content.

**Outcome:** All deliverable files exist and are correctly formatted on disk. No functional impact.

---

### 7.6 Problem — Resisting Scope Creep Toward CRUD

**Context:** Once the domain contract was defined, it was tempting to "just quickly" scaffold an `Allocation.js` model, an `allocationService.js` with `createAllocation()`, a controller, and a route. The entire CRUD surface could have been built in another hour.

**Investigation:** The brief (§3) is explicit — allocation persistence, CRUD APIs, and a new MongoDB collection are *all* out of scope unless a separately approved decision expands the sprint. The brief (§13) is even more direct: *"Do not start by creating an Allocation model or collection."*

**Mitigation:** I stopped at the pure validation layer and left persistence entirely for S3.2. The handoff section of this report specifies exactly what S3.2 needs to do, including the uniqueness index, the state-dependent checks, and the error codes to use. S3.2 will not have to re-derive any domain rules.

**Outcome:** The sprint remained within its approved scope. S3.2 can begin immediately with no ambiguity about the contract to implement.

## 12. Handoff to S3.2 (Allocation Persistence & Service)

The next developer can begin S3.2 immediately. They do **not** need to re-derive any domain rules. The following are already fixed by this sprint:

1. **Fields to persist:** `activityId` (ObjectId, required), `facultyId` (ObjectId, required), `roomId` (ObjectId, required). Nothing else in the base allocation model.
2. **Uniqueness:** Composite unique index on `(activityId, facultyId, roomId)`.
3. **No `institutionId` or `groupId` on Allocation:** both are derived via the Activity reference.
4. **State-dependent validation to add:**
   - Activity exists and belongs to the current institution.
   - Faculty exists and belongs to the current institution.
   - Room exists and belongs to the current institution.
   - Faculty is a member of `activity.facultyIds`.
   - Room is a member of `activity.roomIds`.
   - No duplicate tuple already exists.
5. **Error codes to use:** The 6 pure codes from `ALLOCATION_ERRORS` plus the 8 state-dependent codes documented in the Domain Contract §7.
6. **Institution resolution:** Same `Institution.findOne().sort({ createdAt: -1 })` convention as every other service.
7. **Service location:** `server/core/institution/academic-context/allocationService.js` (new file following existing convention).
8. **Error-throwing convention:** `error.statusCode` + `error.message`, caught by controller via the standard pattern.
9. **Validation ordering:** Call the pure validator from S3.1 first; only perform state-dependent checks if pure validation passes.

## 15. Request for Senior Review

I am specifically requesting review on the following decisions, each of which could reasonably be contested and each of which materially affects S3.2 and S3.3:

1. **Allocation granularity.** Is 1 Activity : 1 Faculty : 1 Room the correct unit, or should the product treat multi-faculty or multi-room allocations as first-class? My recommendation is 1:1:1 because the alternative blurs the eligibility boundary and complicates uniqueness reasoning; a multi-faculty activity is naturally modeled as multiple allocations.

2. **Uniqueness tuple.** Is `(activityId, facultyId, roomId)` the right constraint? It is well-defined in the absence of time semantics but will need to be revisited when time is introduced. Should S3.2 implement this as a composite unique index now, or should it be deferred until time semantics are approved?

3. **Deferred lifecycle.** The contract introduces no status field. Does the product roadmap in the near term require draft/confirmed/cancelled states that would make early adoption cheaper than retrofitting later?

4. **Open questions in Domain Contract §10.**
   - Should allocation creation require the Activity's validation status to be `ready`? I defaulted to **no** because a coordinator may want to allocate partial resources while fixing other issues, but this could reasonably go either way.
   - Should Faculty/Room deletion cascade to Allocations? Currently no cascade behavior exists in Phase 2; S3.2 could introduce it, but only with a documented decision.
   - Should allocation support partial states (e.g., faculty assigned, room TBD)? I defaulted to **no** because this would effectively introduce lifecycle without saying so.

The pure validation module follows the exact same location and conventions as `activityValidationService.js`.
